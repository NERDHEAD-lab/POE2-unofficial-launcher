## 1. 종료 준비를 마친 뒤 한 번만 재시작

**변경 위치**는 재시작 요청을 받는 `main.ts`, 종료 준비와 단일 종료 동작을 조정할 `app-shutdown.ts`, 다운로드 상태와 설치를 소유한 `UpdateHandler.ts`다. 오류 화면의 같은 버튼이 저장을 기다린 뒤, 설치할 업데이트가 있으면 업데이트를 적용해 다시 열고 그 외에는 현재 버전을 다시 연다. 일반 종료의 자동 설치 설정은 유지한다. ## 검증·완료 기준과 승인

1. **구현 시작 조건**은 1단계 재시작의 종료 수명주기 및 다운받은 업데이트의 설치·후속 실행을 업데이트 소유자에게 위임하는 변경과 2단계 로컬 진단 필드에 대한 사용자 승인이다. 권고 범위는 이 두 단계다. 3단계는 제보 빈도만으로 도입하지 않는다. 새 설정 스키마, IPC/EventBus 계약, 의존성, 위 권고를 넘어서는 업데이트 정책 변경이 필요해지면 해당 변경의 영향과 필요성을 별도로 결정한다. 구현 시 `master`와 이 문서의 기준 SHA를 다시 대조하고 이 기능 전용 브랜치로 진행한다.
2. **[Windows-pwsh]** 해당 단계에서 기존 관련 테스트를 `npm test -- --run <대상 테스트 파일>`로 실행한 뒤 `npm run lint`, `npm run build:check` 및 독립 리뷰를 수행한다. 실제 Windows Electron은 고유한 임시 프로필과 합성 데이터로 저장 전후·실패 재시도·트레이 최소화/정상 종료·업데이트 회귀를 확인한다. 1.7.5의 Electron 선언 범위는 `^44.0.0`, lockfile은 44.10.0, 현재 설치된 npm 패키지 표기는 44.1.0이다. 이 차이는 제보 원인으로 판정할 수 없다. 실행한 후보 SHA와 실제 Electron 런타임 버전을 결과에 기록한다. 3. **[사용자]** 동의한 Windows 사용자 환경에서 계정 연결과 POE1·POE2 실행을 확인한다. 로그인 유지 선택 후 정상 종료·재실행, 앱 내 재시작, 지원되는 실제 설치 업데이트 전후에 자격 증명을 다시 요구하는지 각각 확인한다. 일반·QR 로그인, 필요한 보안 인증 표시, 명시적 로그아웃 이후 정상 재로그인을 함께 확인한다. 실제 업데이트는 변경을 포함한 실행본에서 다음 승인된 업데이트로 넘긴 경우와 구버전에서 처음 전환한 경우를 구분한다. 최초 전환 때 종료하는 것은 구버전이다. 다음 배포가 필요한 항목은 별도 결과가 확보될 때까지 미검증으로 남긴다.
4. **승인된 구현의 종점**은 1·2단계의 로컬 후보, 비간섭 검증 및 독립 리뷰다. 공유 데스크톱과 격리 Electron 실행도 사용자 재허용까지 보류한다. 실제 Windows 사용 확인, 원격 push·PR·master 머지, 릴리스는 각각 해당 승인과 검증을 따른다. 실제 개선 효과는 종료 방식과 발생 시각, 재인증 여부가 확인된 후속 사례로 판단한다.

## 구현 및 검증 기록

- 종료 준비를 시작한 요청의 종류와 쿠키 쓰기 결과를 기록한다. 저장과 서비스 정리를 마친 뒤에도 선택된 요청만 최종 동작을 실행한다. 명시적 설치는 먼저 수락한 옵션을 사용하고, 재시작이 먼저 대기한 사이에 다운로드가 끝났으면 설치기에게 후속 실행을 맡긴다. 6.8.11의 `BaseUpdater.quitAndInstall`은 설치 호출 후 다음 이벤트 루프에서 Electron의 `before-quit-for-update`에 이어 `app.quit()`을 요청한다. 이 신호에서 종료를 허용한다. NSIS 실행 성공 여부는 별도 실제 업데이트 검증이 필요하다.
- 같은 파티션에 한 번 설치하는 쿠키 관찰자는 도메인 그룹·수명·원인·제거 여부 조합별 누적 1·2·4·8…회 시점에만 `cookieCount`를 기록한다. 마지막 기록은 관찰 횟수의 하한이다. 세션 전체의 집계를 특정 계정·창에 연결하지 않는다. 현재 카카오 문서에서 수락된 계정 확인과 로그인 필요 신호를 구분하고, 검증 시간 초과와 로그아웃 삭제 완료를 원래 처리 시점에 기록한다.
- **제보 시 선택 공유**. 제보자 PC에서 발생 시각과 종료 방식을 적고, 로그인·재시작 전후 날짜의 로그 ZIP을 로컬에서 연다. 사건 시간대의 로그 레코드 중 `content`가 `[KakaoDiag] `로 시작하는 항목을 기존 `parseKakaoDiagnostic`에 통과시킨다. 반환된 필드만 확인해 직전 실행의 `runId`, 마지막 `session.save`, 다음 실행의 첫 `account.result` 및 해당 시각을 선택해 공유할 수 있다. 원본 ZIP·일반 로그·개인 URL은 제보자 PC에 둔다. 파서로 검증하기 어려우면 발생 시각, 종료 방식, 실제 자격 증명을 요구했는지만 알려 주면 된다. 사건 기록이 빠졌거나 원인을 가를 수 없으면 미상으로 기록한다.
- **[Windows-pwsh]** 별도 checkout에서 lockfile로 설치했다. Node 24.18.0, npm 패키지 Electron 44.10.0 및 electron-updater 6.8.11. 실행한 Electron 런타임은 없다. 원본의 설치 버전은 계획 작성 시의 비교 자료다. 기존 관련 4개 파일 25테스트 통과. 후보의 같은 4개 파일 33테스트 통과. 명령과 로컬 결과는 `.tmp/login-persistence/`에 보존한다.
- **[사용자]** 격리 Electron의 재실행 인스턴스 수·저장 복원, 사용자 계정의 일반·QR 로그인과 로그아웃, POE1·POE2 실행, 실제 업데이트 전환 전후의 재인증 여부는 미검증이다.

### 독립 구현 리뷰

1. **1차 반려.** 대상 33개와 전체 `src` 781개 통과(샘플 의존 9개 건너뜀), 린트·검사용 빌드가 통과한 후보에서도 설치 도중 앞서 시작한 업데이트 확인이 실패하면 전역 오류 리스너가 이를 설치기 실패로 오인할 수 있었다. 6.8.11이 `checkForUpdates()` 실패에 붙이는 문맥과 실제 설치기 오류를 기존 업데이트 리스너에서 구분하도록 수정했다. 회귀 테스트에서 확인 오류 직후에는 안내·종료가 없고 이후 실제 설치기 오류는 처리되는지 검증했다. 기존 중복 설치 테스트에는 서로 다른 무음 옵션을 보내 최초 선택 보존을 확인했다.
2. **2차 통과.** 독립 리뷰어가 수정된 오류 분기와 회귀 테스트에서 확인 오류 직후 안내·종료 0회, 뒤이은 설치 오류에서 자동 설치 해제·안내·종료 각 1회, 중복 설치 요청의 첫 옵션 보존을 확인했다. 수정 후보의 `npm test -- --run` 대상 4파일 33개, `npm run lint`, `npm run build:check`가 통과했다. `npm test -- --run src --maxWorkers=4`는 93파일 781개 통과, 외부 글꼴 샘플 의존 3파일 9개 건너뜀이다. 최종 후보 결과는 `.tmp/login-persistence/targeted-r2.log`, `lint-r2.log`, `build-check-r2.log`, `src-suite-r2.log`에 있다.

**별도 비간섭 최종 QA 통과.** 최종 QA 담당자가 실제 변경분, 수정 후의 검사 로그 및 독립 리뷰 기록을 대조해 승인된 1·2단계 로컬 후보에서 차단 결함이 없음을 확인했다. 실제 Windows 로그인 유지 효과와 단일 재실행·업데이트 설치는 미검증이다. 후보는 후속 실동작 검증과 통합 결정을 위해 별도 checkout에 보존한다.
