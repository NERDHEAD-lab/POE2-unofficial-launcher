# PR-20: RePoE display translation coverage follow-up

> 상위 문서: [../pob-handoff.md](../pob-handoff.md)
> 원천 항목: 사용자 캡처 기반 RePoE/tooltip 번역 누락 follow-up
> 선행 PR: [PR-19](PR-19.md)
> 후속 PR: [PR-21](PR-21.md)

## Goal

Imported Build2와 실제 PoB tooltip/snapshot/search/tree 경로에서 RePoE 표시 번역 누락을 재현 가능한 테스트로 고정하고, tooltip/stat line 번역 coverage, 검색 결과 표시 정책, Tree 로딩 성능 계측/병목 보고, Tree build switch session isolation, 원본 PoB tooltip visual/asset parity, 비-tooltip UI 번역 coverage, 미구현/비활성 컨트롤 표준화, Calcs section visual parity, PR-6 완료 이후 남은 stale placeholder copy, build open 시 mode tab preload/hydration UX, Calcs narrow-width/matrix overflow 스타일, wrapper UI state persistence, Items DB 표시 정책, active build 삭제 guard, Korean item copy parser 보강을 마감한다.
Passive Tree AppData cache와 render layer architecture 최적화는 [PR-22](PR-22.md)로 이관한다.
계획 문서 관리 규칙에 따라 이 문서는 코드 커밋에 포함하지 않고 unstaged 상태로 둔다.

### PR-20.2 Skills/Items search result bilingual display

#### 관찰

- Skills의 `젬 선택 또는 입력`은 현재 `<datalist>` 기반이라 영어 이름으로 검색 가능하지만 결과 표시가 영어/번역 표시 정책과 분리되어 있지 않다.
- Items의 Unique/Rare template 검색도 원본 영어와 설정 언어 번역을 함께 검색 대상으로 쓰지만, 목록 표시는 기본적으로 설정 언어 단일 표기가 되어야 한다.
- 영어 검색어가 원본 영어명에 매칭될 때만 `번역명 (영어명)` 형태로 병행 표기해야 한다.
- 병행 표기 안에서 검색어와 매칭된 영어 글자는 `<mark>` 또는 동등한 inline bold 스타일로 강조해야 한다.
- 설정 언어가 English인 상태에서는 source English와 display text가 동일하므로, 영어 검색어가 매칭되어도 괄호 병행 표기는 표시하지 않고 단일 English label만 표시해야 한다.

#### 원인 분석

- Skills `GemRow`는 translated `availableGems`와 raw `rawAvailableGems`를 모두 `<datalist><option>`에 넣고 있어 rich text highlight가 불가능하다.
- Items DB는 `translateItemDbEntries()`로 표시용 entry를 만들고 `filterTranslatedItemDbEntries()`에서 source/raw entry까지 검색하지만, 어떤 필드가 검색어에 매칭됐는지 메타데이터를 반환하지 않는다.
- 따라서 병행 표기와 bold 처리는 번역 함수 자체가 아니라 검색 결과 projection 단계에서 처리해야 한다.
- translated display text를 PoB action으로 되돌려 보내면 gem id/nameSpec, item id 등 원본 domain이 깨질 수 있으므로 표시와 action payload를 분리해야 한다.

#### 수정 방향

- Skills gem 입력은 `<datalist>`를 커스텀 autocomplete/combobox로 교체한다. 기본 input 값과 commit action은 기존처럼 PoB 원본 gem id/nameSpec domain을 유지한다.
- Items DB 검색은 필터 결과에 display entry, source entry, match source를 함께 담는 view model을 추가한다.
- 기본 목록 표시는 설정 언어명만 렌더링한다. 원본 영어명은 검색 매칭용으로만 사용한다.
- 영어 query가 source English name/base/nameSpec에 매칭되고 설정 언어 표시명과 영어명이 다를 때만 `localized (English)`를 렌더링한다.
- 병행 표기 조건은 `locale !== "en" && matchedSource === "sourceEnglish" && normalized(localized) !== normalized(english)`를 기본 가드로 둔다.
- UI 언어가 English이거나 localized와 English가 같은 경우에는 괄호 병행 표기를 생략한다. 이 경우 영어 검색 highlight가 필요하면 단일 English label 내부에만 적용하고 `English (English)` 형태는 만들지 않는다.
- highlight는 source English segment 안에서만 적용한다. localized query로 검색한 경우에는 병행 표기를 강제로 띄우지 않는다.

#### 주의사항

- 영어 locale에서는 "영어 검색어가 source English에 매칭됨" 조건만으로 병행 표기를 켜면 모든 결과가 `Ice Strike (Ice Strike)`처럼 중복된다. 구현 시 locale/display equality guard를 먼저 적용한다.
- 번역 누락으로 localized display가 source English fallback과 동일한 항목도 병행 표기 대상이 아니다. fallback 상태를 사용자에게 보여줄 별도 UI가 필요하면 PR-20.1 coverage/allowlist에서 다루고, PR-20.2 검색 row에서 괄호 중복으로 표현하지 않는다.
- 검색 view model은 `displayLabel`, `sourceEnglishLabel`, `matchedField`, `shouldShowBilingualLabel`, `highlightRanges`를 분리해 계산한다. 렌더러가 raw query만 보고 병행 표기 여부를 재판단하지 않게 한다.
- highlight는 병행 표기가 켜진 경우 source English segment에 적용한다. 병행 표기가 꺼진 영어 locale에서는 단일 English label에 적용할 수 있지만, localized locale의 localized query 매칭에서는 영어 괄호 표기를 새로 만들지 않는다.

#### 테스트 방향

- `repoeTranslations` 단위 테스트에서 Items DB 검색이 localized name, English name, English base 모두로 매칭되는지 확인한다.
- English name으로 매칭된 결과가 localized display와 source English를 함께 가진 view model을 반환하는지 확인한다.
- localized query 매칭 결과는 source English 병행 표기를 요청하지 않는지 확인한다.
- locale이 `en`인 상태에서 English query가 매칭되어도 view model의 `shouldShowBilingualLabel`이 false이고 `English (English)`가 렌더링되지 않는지 확인한다.
- locale이 `ko`라도 localized display가 source English fallback과 동일하면 `shouldShowBilingualLabel`이 false인지 확인한다.
- Skills view/component 테스트에서 translated gem list 기본 상태가 설정 언어명만 표시하는지 확인한다.
- Skills 영어 검색어 입력 시 `설정 언어명 (English)` 형태의 option row와 영어 segment highlight가 표시되는지 확인한다.
- Skills locale `en` 테스트에서 영어 검색어 입력 시 단일 English option row와 단일 label highlight만 표시되는지 확인한다.

- Items view/component 테스트에서 Unique/Rare template 목록 기본 표시는 설정 언어 단일 표기이고, 영어 검색 시에만 parenthetical English와 highlight가 표시되는지 확인한다.

### PR-20.3 Passive Tree latency instrumentation and bottleneck report

#### 관찰

- 사용자 보고상 이전보다 Tree 데이터를 가져오는 시간이 크게 늘어났다.
- Tree 탭에서 `Fetching tree data...`가 오래 보인다면 `PassiveTreeView`가 아직 `ready` 상태로 전환되지 않은 상태다.
- 현재 `PassiveTreeView`는 탭 활성화 직후 `api.session.treeSnapshot()`과 `api.session.treeMetadata()`를 `Promise.all`로 동시에 요청하고, 둘 다 성공해야 Tree 렌더링 단계로 넘어간다.
- `passiveTreeResourceCache`에는 이미 `window.localStorage["pob:treePerf"] === "1"`일 때 `snapshot`, `metadata`, `resource-manifest`, `resource-load`, `canvas-draw` 시간을 `console.debug("[pob-tree] ...")`로 출력하는 계측이 있다.
- 기존 계측은 renderer console 중심이라 사용자가 전달 가능한 앱 로그 파일에 항상 남는 구조는 아니다.
- 현재 로그만으로는 loading 문구가 `pob.tree.snapshot`, `pob.tree.metadata`, renderer resource manifest/load, ready 이후 projection/translation/draw 중 어디에서 길어지는지 사용자가 전달 가능한 형태로 분리하기 어렵다.

#### 원인 분석

- `Fetching tree data...`가 오래 유지되는 경우 1차 병목 후보는 renderer 이후 리소스 로드가 아니라 main IPC/Lua 쪽의 `pob.tree.snapshot` 또는 `pob.tree.metadata` 응답 지연이다.
- `snapshot` 지연은 Lua `tree_snapshot()` 생성, 빌드의 passive spec 파싱/적용, allocated/path preview 계산, 대형 node payload serialization 비용이 원인일 수 있다.
- `metadata` 지연은 vault `TreeData/<version>/` metadata 추출, asset/connectors/ddsCoords payload serialization, vault path 조회 비용이 원인일 수 있다.
- `resource-manifest` 또는 `resource-load` 지연은 Tree가 ready로 전환된 뒤 이미지/DDS 자산을 불러오는 단계이며, 캐시 키 변경이나 DDS zst decode cache miss가 있으면 체감 렌더링 완료가 늦어질 수 있다.
- `canvas-draw` 지연은 node 수, search highlight, connector/path preview, missing image fallback이 늘어났을 때 발생할 수 있지만 loading 문구 자체를 오래 유지시키는 직접 원인은 아니다.
- RePoE `translateTreeSnapshot()`은 `state.status === "ready"` 이후 `useMemo`에서 실행되므로 loading 문구 이후 병목 후보이며, Tree 표시 지연 또는 interaction jank로 분리해서 봐야 한다.
- PR-20.3에서 cache/keep-alive 구조를 바로 바꾸면 실제 병목이 Lua snapshot인지, metadata인지, resource load인지, ready 이후 projection/translation인지 확인하기 어렵다. 따라서 이 sub-step은 계측과 병목 보고까지로 닫는다.

### PR-20.4 Passive Tree AppData cache and invalidation policy

#### 관찰

- AppData/userData 캐시는 가능하다. `pob-bridge`는 Electron main process에서 동작하고 `app.getPath("userData")`에 접근할 수 있으므로, `pob-tree-cache/<cacheVersion>/...` 같은 별도 디렉터리에 JSON 또는 압축 JSON payload를 저장할 수 있다.
- `pob.tree.metadata`의 connector/assets/ddsCoords/background payload는 vault treeVersion, class/ascendancy, asset set이 같으면 재사용 가능성이 높다.
- Lua `tree_snapshot()`도 static node 좌표/아이콘/연결/프레임/배경과 build-specific allocation/path/dependency/preview 값을 함께 직렬화하므로 cache 대상과 dynamic 대상이 섞여 있다.

#### 원인 분석

- 현재 `readXml()`/`loadBuild()` 경로에는 stable build content hash가 shared contract로 노출되어 있지 않다. 캐시 키는 빌드 파일 경로가 아니라 XML/content hash, PoB vault generation/treeVersion, classId/ascendClassId, cache schema version을 포함해야 한다.
- 저장된 빌드뿐 아니라 draft/import 후 미저장 상태도 고려해야 하므로, 캐시 키는 가능하면 Lua load 입력 XML hash 또는 `saveBuildXml()`/exported XML hash에서 계산해야 한다.
- PoE2 게임 데이터 버전이 바뀌면 같은 XML/content hash라도 passive tree 구조, stat text, asset metadata, RePoE translation baseline이 달라질 수 있으므로 AppData cache를 stale로 취급해야 한다.
- 반대로 build XML/content hash가 바뀌어도 PoE2 게임 데이터 버전과 treeVersion이 같다면 static tree geometry/resource cache는 재사용하고 allocation/path overlay만 리캐싱하는 fast path가 가능하다.

#### 수정 방향

- `snapshot`/`metadata`가 병목이라는 PR-20.3 로그 근거가 있으면 main process에 persistent Tree payload cache를 추가한다.
- 캐시는 `app.getPath("userData")/pob-tree-cache` 하위에 두고, key는 `schemaVersion + game + poe2DataVersion + repoeBaselineVersion + vaultGeneration/treeVersion + xmlHash + classId + ascendClassId`를 기본값으로 한다.
- PoE2 version source는 우선순위를 정해 수집한다. PoB vault/treeVersion이 있으면 1차 기준으로 쓰고, RePoE `version.txt` / `ggpk.exposed version?poe=2` baseline은 RePoE text/asset baseline 검증과 cache namespace 보강에 사용한다.
- cache read 시 저장된 `poe2DataVersion`, `repoeBaselineVersion`, `treeVersion`, `schemaVersion`이 현재 값과 다르면 build hash가 같아도 miss로 처리하고, full Lua snapshot/metadata를 다시 생성해 AppData cache를 갱신한다.
- build hash만 바뀌고 `poe2DataVersion` / `treeVersion`이 같으면 static payload/resource cache는 유지하고 build-specific overlay만 새로 쓰는 방향을 우선한다.
- cache hit 시에는 Lua full snapshot/metadata 호출을 건너뛰거나, 최소 dynamic overlay만 Lua에서 가져와 static cache와 merge한다.
- cache miss 시에는 기존 Lua full snapshot/metadata 결과를 그대로 사용하고, 성공 후 background write로 cache를 저장한다.

#### 테스트 방향

- cache key builder 단위 테스트에서 schemaVersion, game, PoE2 data version, RePoE baseline, treeVersion, XML/content hash, classId, ascendClassId가 모두 key에 반영되는지 확인한다.
- 같은 XML hash라도 PoE2 data version / RePoE baseline / treeVersion이 다르면 cache miss가 나는지 확인한다.
- XML/content hash만 바뀌고 treeVersion/dataVersion이 같을 때 static cache를 재사용할 수 있는지 policy test로 고정한다.
- cache hit/miss 로그가 opt-in 계측 경로와 함께 남는지 확인한다.
- cache miss 또는 cache read 실패 시 기존 full Lua snapshot/metadata fallback이 유지되는지 확인한다.

### PR-20.5 Passive Tree static payload, allocation overlay, and keep-alive

#### 관찰

- 현재 `BuildEditView`는 `activeMode === "tree"`일 때만 `PassiveTreeView`를 렌더링한다. 다른 탭으로 이동하면 Tree 컴포넌트가 unmount되고, 다시 돌아오면 snapshot/metadata 요청부터 다시 시작한다.
- `pob-mode-panel`에는 `key={sessionRevision}`이 걸려 있어 class/ascendancy 변경처럼 `sessionRevision`이 증가하는 작업에서도 패널 subtree가 remount된다.
- `passiveTreeSessionKey`는 현재 `${subPath}/${fileName ?? draft}:${sessionRevision}` 형식이라 build content hash가 아니라 위치/이름/수정 revision 중심의 volatile key다.
- 실제 렌더링에 필요한 좌표/아이콘/연결/프레임/배경 asset 대부분은 동일 treeVersion/class/ascendancy에서는 빌드가 바뀌어도 재사용 가능하고, 빌드별로 주로 달라지는 값은 allocation/path/dependency/preview 계열이다.

#### 원인 분석

- Tree static payload와 allocation overlay를 분리하면 전체 node payload 재직렬화를 줄일 수 있다. 현재 `PobTreeNode`에는 static field와 dynamic field가 섞여 있으므로 shared type/API를 `treeStaticSnapshot` + `treeBuildOverlay` 또는 equivalent 형태로 확장해야 한다.
- keep-alive 방식도 가능하다. 현재는 조건부 렌더링 때문에 Tree 패널 자체가 사라지지만, mode panel 내부에서 Tree를 계속 mounted 상태로 두고 CSS/hidden/aria-hidden으로 숨기면 resource cache, canvas image state, projection state를 유지할 수 있다.
- keep-alive만으로는 빌드 전환 시 allocation 상태가 바뀌는 문제를 해결하지 못한다. 보여주기 직전 또는 build/session 변경 시 lightweight allocation overlay만 갱신하는 API가 필요하다.
- class/ascendancy 변경은 Tree 구조/배경/시작 노드/ascendancy background가 바뀔 수 있으므로 static cache를 보수적으로 invalidate하거나 class/ascendancy를 cache key에 포함해야 한다.

#### 수정 방향

- allocation만 변하는 작업(`pob.tree.allocate`, `pob.tree.deallocate`)은 가능하면 full `PobTreeSnapshot` 반환 대신 overlay delta 또는 updated allocation set을 반환하는 새 contract를 추가한다. 기존 API 호환을 위해 초기는 full snapshot fallback을 유지한다.
- renderer는 `PassiveTreeView`가 static resources/images/projection을 유지할 수 있도록 Tree panel keep-alive를 도입한다. non-active mode에서는 layout/interaction만 숨기고 component state는 유지한다.
- keep-alive 도입 시 tab focus, `aria-hidden`, keyboard navigation, canvas resize observer, tooltip/hover state reset을 함께 처리한다.
- 빌드 전환 시에는 static cache/resource cache는 유지하되, visible 전 또는 sessionKey 변경 시 allocation overlay만 갱신한다. treeVersion/class/ascendancy가 바뀌면 static cache와 resource manifest를 재생성한다.
- RePoE `translateTreeSnapshot()`은 static localized node text 캐시와 dynamic overlay merge 이후 적용하는 방식을 검토한다. 같은 treeVersion/locale에서 반복 번역하지 않는 방향을 우선한다.

#### 테스트 방향

- shared contract test에서 static tree payload와 build overlay가 node id/path/depends/alloc semantics를 보존하는지 확인한다.
- allocation/deallocation action 후 overlay refresh가 stale allocation을 남기지 않는지 focused test로 확인한다.
- BuildEditView tab 전환 시 Tree component/resource state가 유지되고 full snapshot reload가 반복되지 않는지 component/helper test로 확인한다.
- build switch, class/ascendancy change, import, save-as, vault refresh에서 static cache invalidate와 overlay refresh 규칙이 분리되어 동작하는지 확인한다.
- 기존 full snapshot/full render fallback path가 유지되는지 확인한다.

### PR-20.6 Original PoB tooltip visual parity

#### 관찰

- 첨부된 Tree node tooltip은 검은 반투명 배경, 금색/주황색 테두리, 원본 passive header bar, 중앙 정렬 title, magic-colour stat line, stat difference/tip section을 가진다.

- 첨부된 Item tooltip은 rarity별 header art/border, 중앙 정렬 item title/base, armour/quality/socket/requirement metadata, explicit/implicit stat colour, 장착/해제 stat difference red/green block, 하단 tip line을 가진다.
- 현재 unofficial wrapper는 Tree / Item / Skill tooltip을 각각 별도 CSS로 렌더링하며, 원본 PoB header art, separator image, line font/background/center 메타데이터를 충분히 보존하지 않는다.

#### 원본 PoB 코드 분석

- 원본 공통 렌더러는 `src/Classes/Tooltip.lua`의 `TooltipClass`다. `BORDER_WIDTH = 3`, `H_PAD = 12`, `V_PAD = 10`를 사용하고, 배경은 `DrawImage(nil, ..., alpha .85)`로 검은 반투명 패널을 그린 뒤 `tooltip.color`로 외곽선을 그린다.
- `TooltipClass:AddLine(size, text, font, background)`는 line size, font, center, background를 보존한다. `main:WrapString()`으로 maxWidth wrapping도 처리한다.
- `TooltipClass:AddSeparator()`는 `tooltipHeader`가 있으면 rarity/gem별 separator image를 사용한다. item/gem의 첫 separator는 header image와 겹치지 않도록 skip한다.
- `TooltipClass:Draw()`는 `tooltipHeader`별 header image set을 선택한다. item rarity(`RELIC`, `UNIQUE`, `RARE`, `MAGIC`, `NORMAL`), `GEM`, passive tree(`JEWEL`, `NOTABLE`, `PASSIVE`, `KEYSTONE`, `ASCENDANCY`, `ORACLE_*`)가 모두 같은 테이블에서 처리된다.
- `TooltipHost.lua`는 control hover 시 tooltip function을 호출하고 공통 `Tooltip:Draw()`에 위치와 viewport를 맡긴다. 즉 원본은 Tree/Item/Gem이 다른 데이터 생성기를 쓰지만 최종 visual renderer는 공통이다.
- `PassiveTreeView.lua:AddNodeName()`은 node type을 `PASSIVE` / `NOTABLE` / `JEWEL` / `KEYSTONE` / `ASCENDANCY` / `ORACLE_*` header로 매핑하고, node title을 center line으로 추가한다.
- `PassiveTreeView.lua:AddNodeTooltip()`은 node stat lines, jewel socket item tooltip embedding, reminder/flavour text, stat differences, pathing distance, gold cost, warning, Ctrl/Shift tips를 section과 separator로 구성한다.
- `ItemsTab.lua:AddItemTooltip()`은 `tooltip.tooltipHeader = item.rarity`, `tooltip.center = true`, `tooltip.color = colorCodes[item.rarity]`, `tooltip.maxWidth = min(maxWidth, 600)`을 설정하고, item name/base/header influence/stat sections/diff sections를 추가한다.
- `GemSelectControl.lua:AddGemTooltip()`은 `tooltip.tooltipHeader = "GEM"`, `tooltip.color = colorCodes.GEM`, `tooltip.center = true`를 설정하고, `FONTIN SC`, `FONTIN ITALIC`, `GemHoverModBg` background 등 line-level style을 사용한다.

#### 원인 분석

- 현재 Lua bridge의 `new_tooltip_recorder()`는 `AddLine(size, text)`만 의미 있게 기록하고 `font`, `background`, `center`, `tooltipHeader`, `tooltip.color`, `maxWidth`, separator image 같은 visual metadata를 대부분 버린다.
- Shared type `PobTreeTooltipLine`은 `kind`, `text`, `colour`, `size`만 가지고 있어 원본 PoB의 font family, title/header theme, centered lines, alternating stat backgrounds, separator theme을 표현할 수 없다.
- 현재 React 렌더러는 `pob-passive-tree-tooltip`, `pob-item-tooltip`, `pob-skills-tooltip` 세 CSS 경로가 서로 다르다. 그래서 동일한 PoB tooltip data라도 Tree/Item/Skill에서 header, padding, border, separator, typography가 일관되지 않는다.
- Items는 `tooltip.header`를 rarity label 텍스트로 렌더링할 뿐 원본 rarity header image band와 influence icon을 반영하지 않는다.
- Skills tooltip은 `tooltip.header`가 있어도 현재 컴포넌트가 별도 header band를 렌더링하지 않고 line list만 출력한다.
- Tree tooltip은 header theme 없이 단순 title + line list 구조라 passive node type별 원본 header art와 gold/oracle/ascendancy variant를 표현하지 못한다.

#### 수정 방향

- Shared tooltip contract를 공통 rich tooltip 형태로 확장한다. 최소 필드는 `headerType`, `borderColour`, `maxWidth`, line `size`, `font`, `center`, `background`, `colour`, `kind`이다.
- Lua `new_tooltip_recorder()`는 `AddLine(size, text, font, background)` signature를 유지해서 font/background/center를 캡처하고, tooltip 생성 완료 시 `tooltipHeader`, `color`, `maxWidth`, `recipe` 여부를 함께 반환한다.
- React에는 공통 `PobThemedTooltip` renderer를 추가하거나 기존 세 컴포넌트가 공유하는 line/header renderer를 만든다. Tree / Item / Skill은 data source만 다르고 header/theme/line renderer는 같은 규칙을 사용한다.
- 원본 asset을 사용할 수 있으면 PoB vault/resource asset 경로의 `Assets/itemsheader*.png`, `Assets/itemsseparator*.png`, `Assets/*passiveheader*.png`, `Assets/GemHoverModBg.png`를 우선 사용한다. asset 접근이 어렵다면 CSS header slices/gradients로 1차 parity를 구현하되 asset fallback 여부를 문서화한다.

- Skill gem tooltip은 description/flavour line italic 표현, stat set title center, alternating `GemHoverModBg` 배경을 반영한다.
- Tree node tooltip은 node type header, stat diff section, pathing/tip section, socket jewel tooltip embedding을 원본 순서대로 표시한다.

#### 테스트 방향

#### 원인 분석

- 현재 disabled 표현은 busy/loading, 선택값 없음, 원본 PoB 상태상 불가, wrapper 미구현을 같은 `disabled` 속성이나 `is-disabled` class로 섞어 사용한다.
- native `disabled` button/select/input은 click event를 발생시키지 않으므로, "클릭하면 구현 예정 toast를 보여준다"는 UX와 직접 충돌한다.
- Import/Export의 일부 unsupported 버튼은 title/status text가 있지만, 공통 class/data attribute/reason code가 없어 전체 미구현 목록을 정적으로 수집하기 어렵다.
- `packages/pob-ui`에는 launcher settings modal처럼 범용 toast provider가 아직 없다. 그래서 화면별 status line을 임시로 쓰거나, PoB wrapper 전역 toast/status host를 먼저 추가해야 한다.
- `App.tsx`의 `pob-ui-mode-switch`는 `POB_UI_MODES = ["renewed", "legacy"]`를 순회하며 `uiMode.renewed` / `uiMode.legacy` label을 그대로 렌더링한다. 내부 mode identifier는 적절하지만, 사용자 표시 label로는 제품/동작 의미가 약하다.
- UI mode switch는 segmented button처럼 보이지만 방향성이 약하다. `UI 버전 : 레거시 [switch] 비공식`처럼 레거시와 비공식 사이에 실제 switch control을 배치해야 현재 선택된 UI 버전이 스위치 방향으로 드러난다.
- Legacy mode는 원본 PoB parity 확인용이고 Renewed mode는 비공식 wrapper의 개선 UI이므로, 표시 문구는 내부 identifier(`legacy`, `renewed`)를 그대로 노출하지 않는 편이 낫다.

#### 수정 방향

- 구현 예정 컨트롤은 `pob-control-unimplemented` class와 `data-pob-unimplemented="<feature-id>"`, `data-pob-unimplemented-reason="<reason>"` 같은 정형 marker를 사용한다.
- disabled reason을 구분한다. 예: `busy`, `invalid`, `empty-selection`, `source-disabled`, `unsupported`, `not-implemented`. toast 대상은 `unsupported` / `not-implemented`로 제한한다.
- 구현 예정 button은 가능하면 native `disabled` 대신 `aria-disabled="true"`와 guarded `onClick`을 사용해 click/keyboard activation 시 toast를 표시하고 실제 action은 실행하지 않는다.
- select/input처럼 native disabled가 필요한 컨트롤은 wrapper element 또는 옆의 info button에 같은 marker를 달아 클릭 가능한 안내 affordance를 제공한다.
- toast 메시지는 공통 i18n key를 사용한다. 기본 문구는 "아직 구현 예정인 기능입니다."로 두고, feature별 보충 설명을 reason map에서 제공한다.
- PR-20.8 구현 시 먼저 inventory test 또는 static test로 `data-pob-unimplemented` marker 목록을 snapshot화한다. 기능이 구현되면 해당 marker 제거가 테스트 diff로 드러나야 한다.
- UI mode switch는 titlebar에서 `UI 버전 :` label을 앞에 두고, `레거시` label과 `비공식` label 사이에 switch control을 둔다. 선택된 방향은 thumb 위치, active label colour, `aria-checked` 또는 equivalent state로 명확히 보이게 한다.
- 내부 값은 기존 `legacy` / `renewed`를 유지한다. 표시 label만 바꾸고 `DEFAULT_POB_UI_MODE = "renewed"`와 `createPobSnapshotProjection()` 계약은 변경하지 않는다.
- 한국어 label은 `레거시` / `비공식`을 우선 사용한다. 영어 locale에서는 `Legacy` / `Unofficial`처럼 같은 의미의 display label을 둔다.
- UI mode switch 자체는 구현된 기능이므로 항상 `pob-control-unimplemented`를 붙이지 않는다. 다만 향후 특정 mode가 parity 미비로 잠기거나 일부 tab/mode 조합이 구현 전이면 이 switch도 같은 `data-pob-unimplemented` / reason / toast 체계를 사용한다.

#### 테스트 방향

- 공통 `UnimplementedControl` 또는 helper 테스트에서 click, Enter, Space가 toast/status 메시지를 표시하고 실제 action handler를 호출하지 않는지 확인한다.
- native disabled가 필요한 wrapper 케이스에서 안내 affordance가 keyboard accessible인지 확인한다.
- BuildEditView Import/Export unsupported controls에 정형 class/data marker가 붙는지 확인한다.
- UI mode switch가 `UI 버전 : 레거시 [switch] 비공식` 구조로 렌더링되고, selected side와 underlying `uiMode` 값이 일치하는지 확인한다.
- UI mode switch의 mode disabled/not-implemented state가 발생할 경우 공통 class/data marker와 toast path를 사용하는지 확인한다.
- Items / Calcs / Passive Tree의 placeholder disabled controls inventory를 snapshot 또는 focused query 테스트로 고정한다.
- busy/invalid disabled controls에는 구현 예정 toast marker가 붙지 않는지 확인한다.

### PR-20.9 Calcs section visual parity

#### 관찰

- 첨부 사진 1의 현재 wrapper Calcs `ATTRIBUTES` / `RESISTS`는 일반 카드/테이블처럼 보이며, 원본 PoB의 compact stat box 느낌이 약하다.

- 원본은 라벨을 오른쪽 정렬, 값은 왼쪽 정렬로 붙여 좁은 box 안에서 읽게 만든다. 현재 wrapper는 라벨 왼쪽, 값 오른쪽 정렬이라 원본 Calcs 탭의 시선 흐름과 다르다.

#### 원본 PoB 코드 분석

- 원본 공통 렌더러는 `src/Classes/CalcSectionControl.lua`의 `CalcSectionClass:Draw()`다. 모든 Calcs section은 같은 renderer를 통과한다.
- `CalcSectionClass:Draw()`는 `self.colour`로 section 외곽 배경/border를 그리고, 내부는 `SetDrawColor(0.10, 0.10, 0.10)` 검은 패널로 채운다.
- 각 subsection header 위/아래에는 `self.colour` 2px line을 그린다. header text는 `VAR BOLD` 16px이며 label 뒤에 `:`를 붙인다.
- `subSec.data.extra`가 있으면 header label 오른쪽에 `formatCalcStr()` 결과를 그린다. 이 값은 원본 colour code를 포함할 수 있어 Attributes의 Str/Dex/Int, Resists의 Fire/Cold/Lightning summary가 inline colour로 표시된다.
- row label column은 고정 폭 130px에 가깝고 `DrawString(..., "RIGHT_X", 16, "VAR", label .. ":")`로 오른쪽 정렬된다. value cell은 xOffset 134부터 시작해 왼쪽 정렬된다.
- 각 value cell 왼쪽에는 `self.colour` vertical separator가 들어간다. hover/selected breakdown cell은 초록 border를 그리고 내부 배경을 다시 채운다.
- row마다 `rowData.color`, `rowData.bgCol`, `rowData.textSize`를 가질 수 있다. 따라서 label colour, main/offhand/ailment 배경, 작은 text row가 section 단위가 아니라 row 단위로도 달라진다.
- `src/Modules/CalcSections.lua`에서 `Attributes`는 `colorCodes.NORMAL`과 `extra = colorCodes.STRENGTH..Str, colorCodes.DEXTERITY..Dex, colorCodes.INTELLIGENCE..Int`를 사용한다.
- `Resists`는 `colorCodes.DEFENCE`와 `extra = colorCodes.FIRE..Fire + overcap / colorCodes.COLD..Cold + overcap / colorCodes.LIGHTNING..Lightning + overcap`를 사용한다.

#### 추가 스타일 inventory

- `Life`, `Mana`, `Energy Shield`, `Armour`, `Evasion`, `Damage Avoidance`, `Other Defences`, `Damage Taken` 등 section colour가 의미를 가진다.
- `Charges` 계열은 Endurance/Frenzy/Power extra 값을 각각 Rage/Evasion/Mana 계열 colour로 표시한다.
- `Recoup and Hit Taken Over Time`은 header extra와 column header에 Life/Mana/ES colour가 들어간다.

- Renewed UI의 masonry/card 흐름은 유지하되, 각 card 내부는 PoB Calcs section renderer 규칙을 따른다. Legacy UI에서는 더 원본에 가까운 compact fixed-width layout을 별도 모드로 둘 수 있다.

### PR-20.10 Passive Tree build switch session isolation

#### 관찰

- 사용자 캡처에서 Imported Build2 상단 metadata는 Monk / Invoker로 표시되지만, Tree toolbar selector와 중앙 class background는 Ranger로 표시된다.
- Unnamed build는 Ranger / 전직 없음이어야 하는데 이전 Imported Build2의 Invoker 및 할당 노드가 남아 보인다.
- Tree keep-alive 적용 후 mode tab 재진입에서는 full snapshot/translation 반복이 사라졌지만, build 전환 경계에서 stale Tree state가 표시될 수 있다.
- tablist의 데이터를 로드하는 동안 다른 빌드나 다른 탭으로 전환하면 이전 로드가 끝날 때까지 화면 전환이 지연되거나 stale panel이 남는 체감이 있다.

#### 원인 분석

- `BuildEditView`의 `loadState.status === "ready"`는 기존에 현재 props의 `subPath/fileName/draftKey`와 결합되어 있지 않았다. 그래서 build target prop이 바뀐 직후에도 이전 build의 ready state가 한 render 동안 유효했다.
- PR-20.5 keep-alive 구현에서 Tree 슬롯은 `ready` 조건 밖에 있어, 새 build가 Lua session에 load되기 전에도 `PassiveTreeView(active=true)`가 mount되어 이전 Lua session의 `pob.tree.snapshot` / `pob.tree.metadata`를 요청할 수 있었다.
- `pob-mode-panel` key가 `sessionRevision`만 사용해서, 파일이 다른 build로 바뀌어도 sessionRevision이 같으면 Tree/Items/Skills child state가 같은 React subtree 안에 남을 수 있었다.
- 그 결과 상단 build summary/metadata는 새 선택 상태를 따라가지만, Tree canvas/toolbar는 이전 build snapshot 또는 이전 Lua session snapshot을 계속 렌더링하는 split-brain 상태가 가능했다.
- 로딩 중 다른 build/tab으로 전환할 때 지연되는 현상은 active child view가 stale ready state를 보고 async snapshot 요청과 renderer projection/translation을 시작하는 구조와 관련된다. 오래 걸리는 요청 자체를 취소할 수 없더라도, 결과를 현재 build key와 대조하지 않으면 이전 요청 완료 시점에 화면을 덮어쓸 위험이 있다.

#### 수정 방향

- `buildTargetKey = subPath + fileName/draftKey`와 `passiveTreeSessionKey = buildTargetKey + sessionRevision`를 분리해 계산한다.
- ready 판정은 `loadState.status === "ready" && loadState.buildKey === buildTargetKey`로 제한한다.
- `loadBuild()` 완료 시점에 해당 요청이 시작된 `buildTargetKey`를 ready state에 저장하고, 이후 props가 바뀌면 즉시 stale ready를 loading처럼 취급한다.
- `PassiveTreeView` slot은 `ready && uiMode !== "legacy"`일 때만 mount한다. 새 build가 Lua session에 로드되기 전에는 Tree snapshot/metadata 요청을 시작하지 않는다.
- `pob-mode-panel` key는 `passiveTreeSessionKey`를 사용한다. 같은 build/session에서는 tab keep-alive를 유지하되, 다른 build/draft/sessionRevision에서는 child subtree를 remount한다.
- agent harness는 `POE2_AGENT_SECOND_BUILD_NAME`으로 두 번째 build를 선택하고, title/selected build/Tree selector/class/alloc/build metadata class/ascendancy를 `tree-state` JSON으로 남긴다.

#### 테스트 방향

- build session identity helper 테스트로 파일명이 다른 build와 draft key가 다른 build가 같은 sessionRevision이어도 서로 다른 key를 갖는지 확인한다.
- `npm run dev:agent`를 `POE2_AGENT_SECOND_BUILD_NAME='Unnamed build'`로 실행해 Imported Build2와 Unnamed build의 `tree-state` 로그가 각각 현재 선택 build의 class/alloc과 일치하는지 확인한다.
- build 전환 직후 stale Tree canvas가 남지 않고 placeholder/loading 이후 새 Tree snapshot으로 전환되는지 agent 로그와 screenshot으로 확인한다.
- tab warm-return은 같은 `passiveTreeSessionKey` 안에서 `lua-snapshot-delta=0`, `translate-tree-delta=0`을 유지하는지 확인한다.

### PR-20.11 Original PoB tooltip asset-backed renderer follow-up

#### 관찰

- 사용자 캡처의 Item tooltip은 원본 PoB가 game asset 기반 header/separator/border를 사용하는 형태인데, 현재 wrapper tooltip은 rarity/header/separator 메타데이터를 CSS class로 투영한 1차 parity에 가깝다.
- PR-20.6 세 번째 구현에서 `tooltipHeader`, `separatorTheme`, influence/stat-diff metadata는 보존했지만 원본 separator image 자체를 renderer가 직접 로드하지 않는다.
- 따라서 현재 화면은 원본 PoB의 texture asset fidelity보다 낮고, item hover tooltip이 임의 CSS로 그려진 것처럼 보일 수 있다.

#### 원인 분석

- Lua `TooltipClass`는 `tooltipHeader`별 image set을 선택하고 `DrawImage`로 header/separator를 그린다. React renderer는 이 drawing primitive를 받지 않고, metadata를 DOM/CSS token으로 변환한다.
- Passive Tree 렌더러는 vault `TreeData/<version>/` asset loading path를 이미 갖고 있지만, tooltip item/gem header asset은 Tree resource manifest와 별도 경로일 수 있다.
- asset-backed renderer를 적용하려면 vault asset URL/protocol, preload-safe path exposure, renderer cache key, fallback CSS path를 함께 설계해야 한다.

#### 수정 방향

- 원본 PoB `Classes/Tooltip.lua`의 `tooltipHeader` image table과 실제 asset 파일명을 inventory한다.
- 현재 vault/userData 사본에서 해당 asset이 존재하는지 agent/PowerShell 로그로 확인한다.
- Electron preload/main IPC가 renderer에 safe asset URL을 줄 수 있는지 확인하고, 기존 Tree asset loader를 재사용할 수 있으면 공통화한다.
- asset을 찾거나 로드하지 못하면 지금의 CSS fallback을 유지하되, fallback 상태를 코드와 문서에서 명시한다.
- Tree/Skill/Item tooltip 공통 renderer는 header/separator asset loading을 공유하고, line/font/colour metadata와 action/input domain은 기존처럼 display-only로 유지한다.

### PR-20.12 Mode/tab loading responsiveness and stale RPC isolation

#### 관찰

- 사용자는 tablist 데이터를 로드하는 동안 다른 빌드나 다른 탭으로 전환하면 이전 로딩이 끝날 때까지 전환이 지연되는 체감을 보고했다.
- PR-20.10에서 Tree stale state는 build target/session key로 막았지만, in-flight Lua RPC 자체를 취소한 것은 아니다.
- 최신 agent 로그에서도 build switch 시 `lua:pob.tree.snapshot`/`metadata`는 약 0.2~0.8초였고, `translate-tree`는 약 4.35초였다. 이 동안 UI가 target tab/build의 loading shell을 즉시 보여주지 못하면 전환 지연처럼 보인다.
- Items/Skills/Calcs/Config/Party/Notes view는 대부분 `active` effect 안에서 `cancelled` boolean으로 stale state update를 막지만, 이미 시작된 `api.session.*` Promise 또는 PoBSession queue를 중단하지는 못한다.

#### 원인 분석

- Renderer의 `cancelled` flag는 Promise resolution 이후 state update를 막는 장치다. 네트워크/Lua 작업 자체를 abort하는 장치는 아니다.
- `PoBSession.call()`은 내부 `rpcQueue`로 Lua RPC를 순차 실행한다. 긴 snapshot/metadata/config/items request가 이미 들어가면 이후 request는 queue 뒤에 서므로 새 탭/빌드의 요청이 즉시 실행되지 않을 수 있다.
- Tree는 ready 이후 renderer `translateTreeSnapshot()`과 resource load도 길다. 이 구간은 Lua queue가 아니지만 React render/memo 작업이라 tab switch 시 화면 thread를 점유할 수 있다.
- 따라서 "지연"은 세 종류로 나눠야 한다: Lua RPC queue 지연, renderer translation/resource CPU 지연, stale result가 현재 화면에 표시되는 상태 격리 실패.

#### 수정 방향

- 먼저 agent에 rapid tab/build switch scenario를 추가해 `click -> loading shell visible`, `previous request complete`, `new request start`, `new request visible` 시간을 분리한다.
- BuildEditView mode/tab 전환은 target mode shell을 즉시 표시하고, child view의 이전 request 완료를 기다리지 않게 한다.
- child view 공통 request guard는 `buildTargetKey` / `mode` / request token을 포함해 stale result를 버린다. PR-20.10의 Tree guard를 다른 long-load view에도 적용할 수 있는지 검토한다.
- Lua RPC는 현재 cancellable하지 않으므로, cancel token은 우선 renderer-level stale result isolation과 queue timing log에만 적용한다.
- 장기적으로는 PoBSession queue에 priority 또는 stale request coalescing을 넣는 방안을 검토한다. 단, Lua core state mutation action은 순서 보존이 필요하므로 read-only snapshot request와 mutation request를 분리해서 다룬다.
- Tree renderer `translate-tree`는 inactive tab/build 전환 시 work를 중단하거나, locale/treeVersion별 indexed translation cache로 재사용하는 방향을 검토한다.

#### 테스트 방향

- agent rapid-switch log에서 이전 tab/build의 long request가 끝나기 전 target tab/build loading shell이 표시되는지 확인한다.
- stale request가 완료되어도 현재 선택 build/mode state를 덮어쓰지 않는 focused component/helper test를 추가한다.
- read-only Lua request queue timing log가 `previous`, `queued`, `current` request를 구분하는지 확인한다.
- mutation action은 기존 순서 보존을 유지하고 stale coalescing 대상에서 제외한다.

#### 구현 결과

- `BuildEditView`는 `passiveTreeSessionKey` 기준으로 renewed mode panel subtree를 remount하고, 각 mode slot을 hidden mounted panel로 유지한다.
- `getBuildModePreloadOrder()`와 `scheduleHiddenModePreload()`를 추가해 active tab을 우선 표시하고, hidden mode는 `requestIdleCallback` fallback 또는 timeout으로 순차 preload한다.
- Items / Skills / Calcs / Party / Notes는 `preload` prop과 `loadedSnapshotRef`를 받아 hidden hydration 중 read-only snapshot fetch만 수행하고, 같은 panel에서 active 전환 시 재요청하지 않는다.
- Tree는 기존 session key guard를 유지하면서 hidden preload/visible 상태를 분리한다. build switch / draft switch / sessionRevision 변경 시 panel subtree가 remount되어 이전 build data가 남지 않는다.
- Lua RPC 자체는 여전히 non-interruptible queue fallback이다. PR-20에서는 renderer stale display를 막고 target tab shell을 즉시 전환하는 선에서 닫으며, read-only RPC priority/coalescing은 mutation ordering 위험 때문에 PR-22 이후 별도 최적화 후보로 남긴다.
- `scripts/pob-agent-tree.mjs`는 rapid mode switch 시 click elapsed와 final mounted mode 상태를 기록한다. `docs/check/pob-tree-agent-20260529-020258.log` 기준 Imported Build2 rapid switch 후 mounted modes는 `tree, skills, items, calcs, party, notes`, visible mode는 `tree`, placeholder/busy는 false였다.

### PR-20.14 Build open mode preload and hidden tab hydration

#### 관찰

- 현재 `BuildEditView`는 renewed mode에서 active tab 하나만 조건부 렌더링한다. `activeMode === "items"`일 때만 `ItemsView`, `activeMode === "skills"`일 때만 `SkillsView`, `activeMode === "calcs"`일 때만 `CalcsView`가 mount된다.
- 예외적으로 Tree는 PR-20.5/20.10 이후 별도 `.pob-mode-panel-slot` 안에 hidden 상태로 유지되어 같은 build/session 안에서는 warm-return 시 Lua snapshot과 `translate-tree`가 반복되지 않는다.
- Items/Skills/Calcs 등은 탭을 처음 누르는 순간 View가 mount되고 `active` effect가 snapshot RPC를 시작하므로, 사용자는 탭 전환 때마다 loading placeholder가 새로 뜨는 것처럼 느낄 수 있다.
- 사용자 관점에서는 빌드를 열었을 때 각 탭 데이터를 비동기적으로 미리 준비하고, 탭 전환 시 가능한 한 이미 준비된 화면을 보여주는 쪽이 더 자연스럽다.

#### 원인 분석

- `active` prop이 현재 "visible tab"과 "data loading enabled"의 의미를 동시에 가진다. 이 때문에 hidden preload를 하려면 component를 mount하면서도 focus/hover/keyboard/action은 비활성으로 두는 별도 state가 필요하다.
- 모든 mode를 build open 직후 동시에 fetch하면 `PoBSession.call()`의 Lua RPC queue에 read request가 한꺼번에 쌓일 수 있다. 특히 Config/Items/Skills/Calcs snapshot이 동시에 들어가면 active tab 첫 표시가 오히려 늦어질 수 있다.
- 따라서 "전부 미리 렌더링"은 가능하지만, active tab 우선순위와 background preload scheduling 없이 단순 병렬 호출로 구현하면 PR-20.12의 tab/build responsiveness 문제를 악화시킬 수 있다.

#### 수정 방향

- `BuildEditView`는 renewed mode panels를 전부 mount 가능한 구조로 바꾸고, CSS `hidden` 또는 panel visibility class로 표시만 전환한다.
- 각 child view는 `active`를 "visible/interactive" 의미로 유지하고, 별도 `preload` 또는 `enabled` prop으로 hidden snapshot hydration을 시작한다.
- active tab data는 즉시 로드하고, hidden tabs는 `requestIdleCallback` fallback 또는 내부 preload queue로 순차 로드한다. dependency 추가 없이 구현한다.
- read-only snapshot preload는 stale result guard를 session key와 mode key로 묶는다. build switch 시 이전 preload 결과가 새 build panel에 반영되면 안 된다.
- mutation이 있는 action은 preload queue 대상에서 제외하거나 active tab에서만 실행한다. Lua state mutation 순서 보존을 유지한다.
- Tree는 현재 keep-alive 구조를 유지하되, Items/Skills/Calcs/Party/Notes에도 동일한 "mount 유지 + visible만 전환" 원칙을 확장한다.

#### 테스트 방향

- agent에서 build open 후 Tree -> Skills -> Items -> Calcs 순서로 빠르게 전환하고, 이미 preloaded된 탭에서는 loading placeholder가 노출되지 않는지 확인한다.
- preload가 아직 끝나지 않은 탭은 loading shell을 보여주되, 다른 탭 전환을 막지 않는지 확인한다.
- build switch 후 이전 build의 Items/Skills/Calcs snapshot이 새 build에 표시되지 않는지 확인한다.
- active tab의 snapshot 요청이 hidden preload 요청보다 뒤로 밀리지 않는지 timing log로 확인한다.

#### 구현 결과

- renewed mode panel은 `POB_BUILD_MODES.map()`으로 항상 slot을 만들고, visible tab만 `hidden=false`로 둔다.
- hidden slot은 preload queue에 들어간 뒤 mount되고, 한번 loaded된 snapshot은 same session 안에서 재사용된다.
- active tab은 즉시 mount/visible 처리되고 hidden preload는 active tab 이후 순차 실행된다.
- session key가 바뀌면 preload state가 무효화되어 이전 build의 hidden panel snapshot이 새 build에 표시되지 않는다.
- agent rapid-switch scenario로 hidden panel mount 상태와 busy/placeholder 상태를 로그에 남겼다.

- display overlay에서 `Unique Name, Base Name` 형태를 unique name과 base label로 분리해 projection한다.
- row layout은 custom item list처럼 top name / bottom base로 바꾼다.
- source English query가 name에 매칭될 때 name에도 `localized (English)`와 highlight를 적용한다.

### PR-20.18 Active build delete dirty guard

#### 관찰

- 현재 열린 build를 삭제한 뒤 다른 build를 선택하면, 방금 삭제된 build에 대해 저장하지 않은 변경 사항 저장 여부를 묻는 prompt가 뜰 수 있다.

#### 원인 분석

- `Sidebar` 삭제 성공 후 `onSelect()`를 호출하면 `App.requestNavigation()`이 기존 `dirty` state를 보고 unsaved guard를 먼저 평가한다.
- 하지만 active file/folder 삭제는 사용자가 현재 target 자체를 제거한 상황이므로, 삭제된 target 저장 prompt는 의미가 없다.

#### 수정 방향

- 삭제된 item이 현재 active target과 일치하거나 active folder ancestor이면 dirty/pending guard를 초기화하고 삭제 후 target으로 직접 commit navigation한다.
- 일반 navigation의 unsaved guard semantics는 유지한다.

### PR-20.19 Korean custom item equipment property parser

#### 관찰

- 사용자가 전달한 headerless Korean item copy에서 `물리 피해: 19-26` line이 `Unmapped Korean item line` 오류를 발생시킨다.

#### 원인 분석

- 기존 Korean item copy parser는 rarity/header, requirements, item level, sockets, RePoE stat translation reverse map을 처리하지만 equipment property chrome line은 별도 map이 없다.
- `물리 피해:` / `치명타 명중 확률:` / `초당 공격 횟수:`는 stat modifier가 아니라 item property line이므로 stat template reverse map에 걸리지 않는다.

#### 수정 방향

- Korean equipment property label을 English item copy property label로 변환하는 parser path를 추가한다.
- headerless copy는 RePoE reverse name map으로 unique/base/class line을 보수적으로 English로 바꾸고, 알 수 없는 Hangul line은 기존처럼 오류로 남긴다.

### PR-20.20 Item tooltip asset header overlay regression

#### 관찰

- Item tooltip에 원본 PoB header asset을 적용한 뒤, header art가 title/name/base text를 가리는 현상이 있다.

#### 원인 분석

- 현재 구현은 header image를 body 앞에 렌더링하고, 첫 title line을 negative margin으로 header 위쪽에 끌어올린다.
- asset header 높이와 title line 수가 달라지면 text가 header slice 뒤에 숨거나 잘린다.

#### 수정 방향

- asset header container 안에 title/name/base overlay layer를 둔다.
- overlay로 이동한 title lines는 body rendering에서 제외해 중복 표시를 막는다.
- non-asset CSS fallback은 유지하되, asset header path에서는 negative margin 의존을 제거한다.

## Decisions / Risks

- 게임 데이터 번역은 UI i18n JSON이 아니라 `pob-repoe` / display overlay 경로에서 처리한다.
- RePoE CDN/cache 경로를 건드리면 `pob-repoe-data` skill을 사용한다.
- tooltip chrome 문구가 RePoE stat description 대상이 아니면 별도 display-only phrase map으로 분리한다.
- 테스트 allowlist는 임시 은폐가 아니라 의도적 예외를 문서화하는 용도로만 사용한다.
- 검색 결과 병행 표기는 "설정 언어 표시명 + 원본 영어명" 순서로 고정한다.
- 검색 결과 병행 표기는 non-English locale 전용 보조 표시다. English locale 또는 localized/source 동일 항목에서는 영어 검색 매칭이어도 괄호 표기를 생략한다.
- UI i18n JSON에 item/gem name을 추가하지 않는다. item/gem name은 RePoE/display overlay 경로에서만 처리한다.
- PoB Config section/control label처럼 wrapper UI phrase에 해당하는 문구는 item/gem/stat game-data map과 분리한다. ConfigView는 상단 wrapper chrome 제외 본문 전면 coverage 대상으로 보고, Quest Rewards의 일부 stat option 부분 번역은 coverage 완료로 보지 않는다. quest/area/reward 이름은 RePoE source가 있으면 우선 사용하고 없으면 사유가 있는 display-only phrase allowlist로 관리한다.
- Build metadata, build summary, main skill summary 번역 overlay는 display-only다. `classId`, `ascendClassId`, `groupIndex`, Config option value 같은 Lua action/input domain은 바꾸지 않는다.
- Composite socket group label 번역은 구조화된 `group.gems` / `group.activeSkills`를 우선 사용하고, 원문 comma split fallback은 테스트로 고정된 케이스에서만 보수적으로 적용한다.
- 미구현 컨트롤 marker는 실제 구현 누락 추적용이다. busy/loading/선택 없음 같은 일시적 disabled 상태에는 `pob-control-unimplemented` marker를 붙이지 않는다.
- 구현 예정 버튼에 toast를 보여주려면 native `disabled`는 click을 막기 때문에 `aria-disabled` + guarded handler 또는 별도 안내 affordance를 사용한다.
- UI mode switch는 내부 `legacy` / `renewed` mode 값을 유지하되 display label만 `레거시` / `비공식`으로 바꾼다. mode 자체가 구현된 상태라면 미구현 marker를 붙이지 않고, 특정 mode가 잠긴 경우에만 공통 marker/toast를 적용한다.
- Calcs visual parity는 display-only metadata 확장으로 처리한다. breakdown key, cell text value, row/section order, Lua action/input semantics는 변경하지 않는다.
- Calcs rich colour parser는 tooltip rich line 작업과 중복되지 않게 공통 PoB colour-run parser로 공유하는 방향을 우선한다.
- Tree 성능 조사는 PoB Lua 원본 data semantics와 vault asset cache key를 보존한 상태에서 계측부터 진행한다.
- 2026-05-29 agent 로그 기준 Imported Build2의 주 병목은 AppData에 저장할 Lua snapshot/metadata가 아니라 renderer `translate-tree`다. 따라서 persistent AppData Tree cache는 이번 sub-step에서 구현하지 않고, future 로그에서 `lua:pob.tree.snapshot` 또는 `lua:pob.tree.metadata`가 지배적일 때 다시 진행한다.
- persistent cache는 `app.getPath("userData")` 하위 전용 디렉터리에 저장하고, build file path/name만으로는 key를 만들지 않는다.
- cache key에는 최소 schemaVersion, game, PoE2 data version, RePoE/GGPK baseline version, vault/treeVersion, XML/content hash, classId, ascendClassId를 포함한다.
- PoE2 data version 또는 RePoE/GGPK baseline이 바뀌면 XML/content hash가 같아도 AppData cache를 miss 처리하고 리캐싱한다.
- XML/content hash만 바뀌고 PoE2 data version/treeVersion이 같으면 static tree/resource cache를 재사용하고 dynamic overlay cache만 갱신하는 방향을 우선한다.
- static tree payload와 allocation overlay를 분리하더라도 Lua 원본 node id, path, depends, alloc semantics는 유지한다.
- keep-alive는 UI 표시 최적화이며, build/session 변경 시 stale allocation을 보여주지 않도록 visible 전 overlay refresh를 우선한다.
- Tree keep-alive는 같은 `passiveTreeSessionKey` 안에서만 snapshot/resource/canvas state를 유지한다. build target, draft key, sessionRevision이 바뀌면 panel subtree를 remount하고, 새 build가 Lua session에 load 완료되기 전에는 Tree snapshot/metadata 요청을 시작하지 않는다.
- RePoE translation snapshot은 BuildEditView 안에서 locale별로 재사용한다. 이 캐시는 renderer session 최적화이며, 향후 RePoE cache refresh나 locale resource reload를 UI에서 직접 제공하면 locale cache invalidation을 함께 추가해야 한다.
- debug instrumentation은 PR-20 구현 완료 시 제거하거나 `pob:treePerf` 같은 명시적 opt-in 조건 뒤에 남긴다.
- Tooltip visual parity는 display-only metadata 확장으로 처리한다. `font`, `background`, `tooltipHeader` 같은 style metadata를 Lua action/input으로 되돌려 보내지 않는다.
- 원본 PoB asset header/separator 이미지는 가능하면 재사용한다. PR-20.11 후속 구현에서 Tree / Skill / Item tooltip은 공통 asset-backed header renderer를 공유하고, asset을 찾지 못한 경우에만 CSS fallback을 유지한다.
- PoBSession Lua RPC는 현재 queue 기반 순차 실행이며 renderer cancel flag가 in-flight RPC를 중단하지 않는다. tab/build 전환 responsiveness 개선은 stale result isolation, immediate loading shell, read-only request priority/coalescing 가능성을 분리해서 검토한다.
- build open 시 모든 mode panel을 미리 mount/hydrate하는 것은 가능하지만, 단순 병렬 RPC 호출은 active tab 응답을 지연시킬 수 있다. active tab priority + idle/serial hidden preload가 기본 방향이다.
- PR-20은 Lua RPC cancel/priority queue를 구현하지 않는다. read-only RPC coalescing과 persistent resource cache는 PR-22 최적화 범위에서 다시 측정 후 판단한다.
- wrapper UI state persistence는 PoB wrapper 전용 settings domain이다. build explorer/main skill panel 상태는 `PobSettings`와 `pob.settings` IPC/config store만 확장하고 launcher-wide AppConfig에는 추가하지 않는다.
- active target 삭제는 일반 navigation이 아니라 대상 제거 완료 후 정리 경로로 취급한다. 삭제된 build/folder에 대해 unsaved prompt를 띄우는 것은 의미가 없으므로 dirty/draft guard를 reset한다.
- Korean item copy parser는 item property chrome line과 stat modifier line을 분리한다. 알 수 없는 Hangul line은 기존처럼 명시적 오류를 유지해 조용한 오역을 피한다.
- Item tooltip asset-backed header는 텍스트를 asset 아래에 배치하지 않는다. header art와 title/name/base는 같은 container의 z-layer로 분리하고, body에서는 중복 렌더링하지 않는다.
- 새 dependency는 사용자 확인 전 추가하지 않는다.
