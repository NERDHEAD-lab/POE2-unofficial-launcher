## Issue Notes

### PR-21.1 Tree tooltip passive header title/recipe parity

#### 관찰

- 원본 PoB Tree tooltip은 노드 이름 `Killer Instinct`만 passive header asset 안에 표시하고, 옵션 stat line은 아래 본문에 표시한다.
- 원본 PoB는 특정 notable 노드의 정제된 감정 recipe를 이름 오른쪽에 함께 표시한다. 제보 캡처의 `Killer Instinct`는 `Greed`, `Paranoia`, `Greed`가 각 아이콘과 함께 표시된다.
- 현재 wrapper Tree tooltip은 header asset 안에 `Killer Instinct`뿐 아니라 `40% increased Attack Damage ...`, `60% increased Attack Damage ...` stat line까지 들어가며, 좁은 header 내부에서 말줄임 처리된다.
- 현재 wrapper Tree tooltip에는 원본 PoB의 정제된 감정 recipe 표시가 없다.

#### 재현 조건

- Tree 탭에서 정제된 감정 recipe가 있는 notable 노드에 hover한다.
- 확인 대상 예시: PoB `TreeData/0_4/tree.lua` 기준 `Killer Instinct`, skill id `56453`, recipe `Greed / Paranoia / Greed`.

#### 기대 동작

- passive/notable/keystone header asset 영역에는 노드 이름 첫 줄만 들어간다.
- recipe가 있는 노드는 원본 PoB처럼 title line 오른쪽에 recipe 이름과 아이콘을 inline으로 표시한다.
- stat line과 compare/tip/gold line은 tooltip 본문 영역에 표시하며 header asset 내부로 이동하지 않는다.
- renderer 표시만 보강하고, Lua action/input domain에는 translated display text를 되돌려 보내지 않는다.

#### 원인 분석

- 원본 PoB `Classes/PassiveTreeView.lua:AddNodeName()`은 `tooltip:SetRecipe(node.infoRecipe)` 후 `tooltip.tooltipHeader = "NOTABLE"` 같은 passive header를 설정하고, `tooltip:AddLine(24, nodeName, "FONTIN")`으로 첫 줄 노드 이름만 추가한다.
- 원본 PoB `Classes/PassiveTree.lua`는 `node.recipe`를 순회해 `node.infoRecipe = { name = oil, sprite = self:GetAssetByName(oil) }` 형태로 준비한다. `TreeData/0_4/tree.lua`에는 `Killer Instinct` recipe가 `Greed / Paranoia / Greed`로 들어 있고, 감정 아이콘은 `ddsCoords["oils_108_108_RGBA.dds.zst"]`의 `Greed`, `Paranoia` layer로 제공된다.
- 원본 PoB `Classes/Tooltip.lua:CalculateColumns()`는 `self.recipe and i == 1`일 때 첫 번째 line만 title+recipe로 별도 처리하고 `_handled` 처리한다. 이후 stat line은 일반 line으로 계속 그린다.
- 현재 bridge `packages/pob-headless-glue/resources/lua/ipc_bridge.lua`의 recorder는 `tooltip:SetRecipe(recipe)`에서 `self.recipe`를 저장하지만, `tree_node_tooltip()` 반환값은 `nodeId`, `header`, `lines`만 포함한다. 따라서 recipe 정보가 renderer까지 전달되지 않는다.
- 현재 renderer `packages/pob-ui/src/views/pobTooltipAssetParts.ts`의 `collectPobTooltipHeaderTitleEntries()`는 첫 separator 이전의 모든 non-empty line을 header title entry로 수집한다.
- Passive Tree tooltip은 원본 PoB에서도 노드 이름 뒤 stat line 앞에 separator를 넣지 않는다. 그래서 wrapper는 첫 separator 전 stat line까지 header title로 오인하고, `PobTooltipAssetHeader`가 이를 header asset 내부에 렌더링한다.
- 현재 `packages/pob-ui/src/views/pobTooltipAssets.ts`의 passive header theme는 height/side width가 원본 PoB `Tooltip.lua`의 passive header config와 다르다. 이 차이는 header 내부 줄 겹침/말줄임을 더 눈에 띄게 만들 수 있으므로 구현 시 원본 수치와 asset 실제 렌더 결과를 같이 재확인해야 한다.

#### 수정 방향

- Passive Tree tooltip용 header title 수집 규칙을 Items/Skills tooltip과 분리한다. Tree에서는 첫 non-empty title line만 header asset title로 취급하고, stat line은 separator 위치와 무관하게 본문으로 남긴다.
- `PassiveTreeView.tsx`에서 header title로 skip하는 line index도 첫 title line에만 적용한다. 현재처럼 first separator 전 전체 line을 본문에서 제거하지 않는다.
- recipe 표시 계약을 추가한다. 우선 후보는 `PobTreeNodeTooltip.recipe?: { name: string; assetName?: string | null }[]`이며, bridge는 `tooltip.recipe` 또는 `node.recipe`를 기반으로 recipe 이름을 전달한다.
- recipe 아이콘은 Tree metadata의 `ddsCoords`/`assets`에서 recipe name(`Greed`, `Paranoia`)을 `resolveDdsAssetRef()`로 찾아 렌더링한다. icon asset resolve가 실패하면 이름 text만 표시하고 테스트에서 실패 원인을 볼 수 있게 한다.
- `Greed`, `Paranoia` 같은 recipe 이름은 게임 데이터 표시 영역이므로 UI i18n JSON이 아니라 RePoE/display overlay 경로로 번역 가능성을 검토한다. 단, 원본 PoB parity 확인 단계에서는 먼저 원문 recipe 구조와 아이콘 표시를 맞춘다.
- passive header asset 크기와 padding은 원본 PoB `Tooltip.lua`의 `PASSIVE/NOTABLE/KEYSTONE/ASCENDANCY/JEWEL/ORACLE_*` config를 기준으로 재검토한다.

#### 테스트 방향

- `collectPobTooltipHeaderTitleEntries()` 또는 새 Tree 전용 helper 테스트에 `title`, blank line, stat lines, separator 순서의 fixture를 넣고 첫 title line만 header entry가 되는지 고정한다.
- shared contract test에 Tree tooltip recipe field를 추가하고, 기존 tooltip payload는 recipe가 없어도 호환되게 optional로 둔다.
- bridge/imported build focused test에서 recipe가 있는 passive node를 찾아 `treeNodeTooltip()`이 recipe 이름을 반환하는지 확인한다.
- renderer/component test 또는 `npm run dev:agent` screenshot으로 `Killer Instinct` hover 시 stat line이 header 아래에 있고 recipe가 title 옆에 표시되는지 확인한다.
- Windows PowerShell full validation은 구현 goal에서 `npm run lint`, `npm test`, `npm run build:check`로 수행한다.

### PR-21.2 Skills gem tooltip translation coverage

#### 관찰

- 스킬젬 목록/입력의 gem 이름은 설정 언어로 표시된다.
- 제보 캡처의 `파생하는 균열 I` tooltip은 header title의 gem 이름만 한국어이며 나머지 대부분이 영어다.
- 영어로 남는 라인은 `Support`, `Category: Fissures`, `Tier: 3`, `Cost Multiplier: 120%`, 설명 문단, `Supported Skills' ... (Not supported in PoB yet)` stat line이다.
- 전체 tooltip 번역이 빠진 것은 아니며, 이름 번역만 기존 `gemNamesBy...` map으로 성공하고 나머지 line coverage가 없는 상태로 보인다.

#### 재현 조건

- 언어를 한국어로 설정한다.
- Skills 탭에서 support gem tooltip을 연다.
- 확인 대상 예시: `Branching Fissures I` / `파생하는 균열 I`, 원본 PoB 데이터 `SupportBranchingFissuresPlayer`.

#### 기대 동작

- gem 이름뿐 아니라 tooltip metadata, 설명, stat line, unsupported suffix가 설정 언어로 표시된다.
- Lua/PoB로 전달하는 gem id, `nameSpec`, skill id, stat id domain은 원본 영어/ID를 유지하고, renderer 표시 텍스트만 번역한다.
- 영어 locale에서는 병행 표기나 한국어 overlay 없이 원본 영어 tooltip을 그대로 유지한다.

#### 원인 분석

- renderer `packages/pob-ui/src/views/SkillsView.tsx`는 `SkillsGemTooltip` 렌더 전 `translateSkillsGemTooltip(tooltip, translations)`를 호출한다. 따라서 tooltip 렌더링이 번역 함수를 우회하는 문제는 아니다.
- `packages/pob-repoe/src/displayTranslations.ts`의 `translateSkillsGemTooltip()`은 `header`와 `lines`를 `translateTooltipLines()`로 넘기고, 각 line은 `translateDisplayText()` 하나에 의존한다.
- 현재 `translateDisplayText()`가 안정적으로 처리하는 것은 gem/item name, 일부 수동 PoB phrase, requirement chrome, stat translation exact/template 정도다. 스킬젬 tooltip 전용 chrome(`Support`, `Category`, `Tier`, `Cost Multiplier`, `Reservation`, `Cooldown`, `Quality`, `Attack Damage`, `Cast Time` 등)은 별도 coverage가 부족하다.
- `packages/shared/src/types.ts`의 `PobRepoeTranslationsSnapshot`은 `gemNamesById`, `gemNamesBySkillId`, `gemNamesByEnglishName`만 갖고 있으며 skill/gem description, gem family/tag, tooltip chrome phrase를 담을 필드가 없다.
- RePoE translation indexer `packages/pob-repoe/src/translations.ts`도 `skill_gems.json` / `skills.json`에서 이름만 `gemNamesBy...`로 색인한다. 설명/카테고리/태그/지원젬 family는 색인하지 않는다.
- 원본 PoB `Classes/GemSelectControl.lua:AddGemTooltip()`은 `gemInstance.gemData.gemType`, `tagString`, `gemFamily`, `Tier`, `grantedEffect.levels[*].manaMultiplier`, `grantedEffect.description`, `AddStatSetInfo()`를 순서대로 tooltip line으로 합성한다.
- `AddStatSetInfo()`는 `build.data.describeStats(stats, statSet.statDescriptionScope)`로 stat descriptions를 만든다. 이 line은 RePoE `stat_translations/*` template과 매칭될 수 있지만, 현재 캡처처럼 `main.notSupportedModTooltips`가 붙인 `(Not supported in PoB yet)` suffix가 있으면 exact/template 매칭이 실패할 가능성이 높다.
- bridge `packages/pob-headless-glue/resources/lua/ipc_bridge.lua`의 `skills_gem_tooltip()`은 `groupIndex`, `gemIndex`, `mode`, `header`, `lines`만 반환한다. 각 line이 gem type/chrome/description/stat description 중 어디서 왔는지 source metadata가 없어서 renderer가 문맥 기반으로 번역하기 어렵다.

#### 수정 방향

- 스킬젬 tooltip 전용 display translator를 추가한다. `translateSkillsGemTooltip()`에서 일반 `translateTooltipLines()`만 호출하지 말고 gem tooltip line classifier를 먼저 적용한다.
- tooltip chrome coverage를 추가한다:
  - `Support` -> 설정 언어
  - `Category: <family>` -> label과 family name 번역
  - `Tier: <n>`, `Level: <n>`, `Quality: +n%`, `Cost Multiplier: n%`, `Cost & Reservation Multiplier: n%`, `Reservation Multiplier: n%`, `Additional Reservation: n Spirit`, `Cooldown Time: n sec`, `Attack/Cast/Critical Hit/Requires` 계열
- `PobRepoeTranslationsSnapshot` 확장 후보:
  - `skillDescriptionsById`
  - `skillDescriptionsByEnglishText`

### PR-21.4 Existing build save overwrite semantics

#### 관찰

- 기존 `Imported Build2`를 수정한 뒤 저장하려고 하면 상단 오류로 `EXIST: file already exists, open 'C:\Users\...\Documents\Path of Building (PoE2)\Builds\Imported Build2.xml'`가 표시된다.
- 화면에는 unsaved-change dialog가 떠 있고, `저장` 버튼을 누르는 기존 build 저장 흐름에서 파일명 중복 오류가 발생한다.
- 새 빌드 생성이나 Save As에서 같은 파일명이 이미 있는 경우라면 충돌 방지가 맞지만, 현재처럼 이미 열려 있는 기존 build를 수정 후 저장하는 경우에는 같은 파일을 overwrite해야 한다.

#### 재현 조건

- Build list에서 기존 XML build를 연다.
- Tree/Skills/Items/Calcs/Notes 등에서 dirty 상태가 되도록 수정한다.
- 저장 버튼 또는 다른 build/tab/window 이동 중 뜨는 unsaved-change dialog에서 `저장`을 누른다.
- 기존 파일명과 동일한 경로에 저장하려고 할 때 `EEXIST` 오류가 표시된다.

#### 기대 동작

- 기존 build의 일반 저장은 원본 PoB처럼 현재 XML 파일에 overwrite된다.
- 새 build/draft 저장 또는 Save As/이름 변경 성격의 저장은 기존 파일이 있으면 충돌을 막고 사용자에게 다른 이름을 요구한다.
- 저장 성공 시 dirty flag는 false가 되고, build list refresh와 selected target은 저장된 기존 파일을 계속 가리킨다.
- 저장 실패 시에는 dirty flag를 false로 낮추지 않고, 사용자가 다시 저장/취소/버리기를 선택할 수 있어야 한다.

#### 원인 분석

- renderer `packages/pob-ui/src/views/BuildEditView.tsx`의 `saveCurrent()`는 현재 `fileName`이 있으면 `saveBuildAs(fileName)`을 호출한다.
- `saveBuildAs()`는 `api.session.saveBuildXml()`로 현재 PoB session XML을 export한 뒤 `api.builds.saveXml(subPath, nextFileName, exported.xml)`을 호출한다.
- main/bridge `packages/pob-bridge/src/buildsScanner.ts`의 `builds:save-xml` handler는 `fs.writeFile(path.join(dir, ensureXml(fileName)), xml, { flag: "wx" })`를 사용한다.
- Node `wx` flag는 exclusive create라서 target file이 이미 있으면 `EEXIST`가 난다. 그래서 기존 build 저장도 신규 파일 생성처럼 처리되어 현재 파일과 같은 이름이면 실패한다.
- `builds:save-stub`도 `flag: "wx"`를 사용한다. 이 경로는 새 build stub 생성이므로 충돌 방지 의미가 맞고 유지해야 한다.
- 원본 PoB `Modules/Build.lua:SaveDBFile()`은 기존 `self.dbFileName`이 있으면 `io.open(self.dbFileName, "w+")`로 같은 파일을 overwrite한다.
- 원본 PoB `OpenSaveAsPopup()`은 새 이름 저장 시 `io.open(newFileName, "r")`로 파일 존재 여부를 확인하고, 이미 있으면 Save 버튼을 비활성화한다. 즉 기존 저장과 Save As 중복 방지는 별도 의미다.
- 현재 wrapper IPC/API에는 `create only`와 `overwrite existing current file`을 구분하는 명시적 저장 모드가 없다. `saveXml` 하나가 draft/new/current 저장에 모두 쓰이면서 current save까지 exclusive create 정책을 탄다.

#### 수정 방향

- 저장 API에 의도를 분리한다. 후보:
  - `builds.saveXml(subPath, fileName, xml, { overwrite: true })`처럼 옵션 추가
  - 또는 `saveXml`은 기존처럼 create-only로 두고 `overwriteXml`/`saveExistingXml` IPC를 별도 추가
- `BuildEditView.saveCurrent()`는 현재 열린 기존 build 저장이므로 overwrite 모드로 저장한다.
- `saveDraftAs()`와 새 build 생성/Save As 성격 저장은 create-only 모드를 유지한다. 같은 이름 충돌은 `EEXIST`를 사용자 친화적인 중복 이름 메시지로 변환한다.
- overwrite 구현은 가능하면 `write temp file -> rename` 방식으로 atomic에 가깝게 처리해 저장 중 실패 시 기존 XML 손상 가능성을 줄인다.
- overwrite는 현재 선택된 `subPath/fileName`에 한정한다. 임의 이름 overwrite는 Save As 충돌 방지와 섞지 않는다.
- 저장 성공 후 `onDirtyChange(false)`, `onSavedAs(fileName)`, App의 `setDirty(false)`, `setRefreshToken()` 순서가 기존 build target을 바꾸지 않는지 확인한다.

#### 테스트 방향

- `buildsScanner` 테스트에 기존 XML이 있는 경우 overwrite 저장이 성공하고 내용이 교체되는 케이스를 추가한다.
- 같은 테스트에서 `save-stub` 또는 create-only 저장은 기존 파일이 있으면 계속 실패하는지 고정한다.
- `BuildEditView` 또는 저장 helper 테스트에서 `saveCurrent()`는 overwrite 모드를 호출하고, `saveDraftAs()`는 create-only 모드를 호출하는지 확인한다.
- `unsavedBuildGuard`/App flow 테스트에서 기존 dirty build의 pending dialog `저장`이 `EEXIST` 없이 성공하고 dialog가 닫히는지 확인한다.
- 저장 실패 시 dirty flag가 유지되고 error banner가 표시되는지 확인한다.
- Windows PowerShell full validation은 구현 goal에서 `npm run lint`, `npm test`, `npm run build:check`로 수행한다.

### PR-21.6 Item detail tooltip full-height asset/background wrapping

#### 관찰

- Items 상세 보기의 `보기` 모드에서 rich item tooltip border/background가 tooltip 내용 전체를 감싸지 못한다.

- header asset과 separator asset은 상단에는 정상 표시되지만, tooltip container height가 content height를 따라가지 못해 전체 item card가 하나의 박스로 보이지 않는다.
- floating hover tooltip보다는 오른쪽 상세 보기 embedded tooltip에서 두드러진다.

#### 재현 조건

- Items 탭에서 stat difference line이 긴 custom/rare item을 선택한다.
- 오른쪽 상세 패널을 `보기` 모드로 둔다.
- item tooltip의 comparison line이 패널 높이를 넘어갈 만큼 길어질 때, tooltip border/background가 line 끝까지 이어지는지 확인한다.

#### 기대 동작

- item tooltip border, background, header/separator asset은 tooltip content 전체 높이를 기준으로 렌더링된다.
- detail panel은 전체 tooltip box를 하나의 scroll content로 다루며, 스크롤해도 content가 border 밖으로 새지 않는다.
- parent panel 높이가 작아도 embedded tooltip box 자체가 shrink되지 않고 content 높이를 유지한다.
- floating tooltip은 viewport 안에 맞추기 위해 내부 스크롤을 갖는 현재 동작을 유지한다.

#### 원본 PoB 레이아웃 분석

- 원본 `Classes/Tooltip.lua:GetSize()`는 모든 line/separator의 height를 합산해 `ttH`를 계산한다.
- `Tooltip.lua:CalculateColumns()`는 line을 drawStack에 쌓으며 `maxColumnHeight = max(y - ttY + 2 * BORDER_WIDTH, maxColumnHeight)`로 실제 content 높이를 갱신한다.
- `Tooltip.lua:Draw()`는 `maxColumnHeight` 기준으로 검은 background를 그리고, 마지막에 left/right/top/bottom border를 같은 높이로 그린다.
- 즉 원본 PoB tooltip은 visible area 높이가 아니라 content 계산 결과를 기준으로 background와 border를 그린다. viewport를 넘을 때는 위치 조정 또는 column break를 사용하며, content line이 border 밖으로 흘러나오는 구조가 아니다.

#### 원인 분석

- wrapper `packages/pob-ui/src/views/ItemsView.tsx`의 상세 보기에서는 `<aside className="pob-items-detail">` 안에 `ItemDetail`이 렌더링되고, `보기` 모드일 때 `RichItemTooltip`이 embedded child로 들어간다.
- `packages/pob-ui/src/styles.css`의 `.pob-items-detail`은 `display: flex`, `flex-direction: column`, `overflow: auto`, `min-height: 0`이다.
- `.pob-item-tooltip`은 `display: flex`, `flex-direction: column`, `min-height: 0`이고 별도 `flex-shrink` 방지가 없다. flex column parent 안에서 기본 `flex: 0 1 auto`로 shrink 가능하다.
- 긴 tooltip이 detail panel 남은 높이보다 커지면 `.pob-item-tooltip` box가 shrink되고, normal-flow line content가 border/background box 밖으로 overflow되어 보일 수 있다.
- floating tooltip은 `.pob-item-tooltip.is-floating`에서 `position: fixed`, `overflow-y: auto`를 따로 갖는다. 따라서 embedded detail tooltip과 floating tooltip의 overflow 정책을 분리해야 한다.

#### 수정 방향

- embedded tooltip에는 shrink 방지 규칙을 추가한다. 후보:
  - `.pob-items-detail > .pob-item-tooltip { flex: 0 0 auto; }`
  - 또는 `.pob-item-tooltip:not(.is-floating) { flex: 0 0 auto; }`
- `.pob-item-tooltip`의 `min-height: 0`이 embedded card 높이 계산을 방해하면 제거하거나 floating/scroll container 전용으로 제한한다.
- detail panel은 지금처럼 `overflow: auto`를 유지해 전체 tooltip card를 스크롤한다. tooltip 내부에 별도 스크롤을 만들지 않는다.
- floating tooltip은 viewport 제한을 위해 `.is-floating`의 `overflow-y: auto`와 max-height 정책을 유지한다. embedded fix가 floating hover tooltip에 적용되지 않게 selector를 분리한다.
- asset header/separator 자체보다는 tooltip container sizing 문제로 보이므로, PR-21.3/21.5의 asset header translation/layout 수정과 함께 screenshot regression으로 확인한다.

#### 테스트 방향

- component/style test 또는 Playwright agent screenshot에서 긴 item comparison tooltip이 embedded detail viewer 안에서 border/background 끝까지 감싸는지 확인한다.
- `.pob-items-detail` 스크롤 상태에서 tooltip card bottom border가 마지막 line 아래에 위치하는지 screenshot assertion 또는 DOM bounding box check를 추가한다.

### PR-21.9 Dismissible/copyable error banner actions

#### 관찰

- 오류가 발생하면 상단에 `pob-error` banner가 표시되는 것은 좋지만, 현재 사용자가 바로 오류 내용을 복사하거나 banner를 닫을 수 있는 조작이 없다.
- 기존 캡처의 `EEXIST: file already exists...` 같은 긴 오류는 사용자가 보고서로 전달하기 위해 직접 드래그/복사해야 한다.
- 닫기 조작이 없어서 일시적 오류가 해결된 뒤에도 다음 state update 전까지 화면 상단을 차지할 수 있다.

#### 재현 조건

- 기존 build 저장 실패, build load 실패, Items/Skills/Config/Calcs action 실패 등 `pob-error`가 표시되는 오류를 발생시킨다.
- 상단 오류 메시지 오른쪽에 복사/닫기 조작이 없고, 오류 보고서 복사가 불가능한지 확인한다.

#### 기대 동작

- 오류 banner 오른쪽에는 `content_copy`와 `close` icon button이 표시된다.
- 복사 버튼은 표시 메시지만이 아니라 보고에 필요한 최소 컨텍스트를 포함한 텍스트를 clipboard에 복사한다.
- 복사 성공/실패는 짧은 상태 표시나 기존 notice/toast 패턴으로 알려준다.
- 닫기 버튼은 현재 banner를 숨긴다. 이후 같은 action에서 새 오류가 발생하면 다시 표시되어야 한다.
- 버튼은 keyboard focus, `aria-label`, `title`을 갖고, 좁은 폭에서도 오류 메시지 텍스트와 겹치지 않아야 한다.

#### 원인 분석

- 현재 `packages/pob-ui/src/styles.css`의 `.pob-error`는 단순 text container다. layout은 `margin`, `padding`, `background`, `border`, `color`만 정의되어 action area가 없다.
- 전역 상단 오류는 `packages/pob-ui/src/App.tsx`의 `{error && <div className="pob-error">{error}</div>}`와 `packages/pob-ui/src/views/Sidebar.tsx`의 `{error && <div className="pob-error">{error}</div>}`처럼 직접 렌더링된다.
- view별 오류도 `BuildEditView`, `ItemsView`, `SkillsView`, `ConfigView`, `CalcsView`, `NotesView`, `PartyView`, `PassiveTreeView`, `LegacyModeView`, `VaultSettingsModal` 등에서 `pob-error`를 직접 사용한다.
- 따라서 복사/닫기 기능을 CSS만으로 추가할 수 없고, 최소한 공통 `PobErrorBanner` 같은 컴포넌트가 필요하다.
- 이미 Import/Export build code는 `navigator.clipboard.writeText(...)`와 `content_copy` material icon을 사용한다. launcher fatal error modal도 오류 보고서 복사 흐름을 갖고 있다. PoB wrapper 오류 banner도 같은 clipboard API와 material icon 스타일을 재사용할 수 있다.
- 모든 `pob-error`를 한 번에 바꾸면 load-blocking error와 dismissible action error semantics가 섞일 수 있다. 특히 load 실패 화면에서 오류를 닫았을 때 빈 화면이 되지 않도록 close 가능 범위를 구분해야 한다.

#### 수정 방향

- 공통 컴포넌트 후보: `PobErrorBanner`.
  - props: `message`, `source?`, `details?`, `dismissible?`, `onDismiss?`, `copyable?`, `buildContext?`
  - 기본 class는 기존 `.pob-error` tone을 유지하고, 내부를 `message + actions` flex layout으로 바꾼다.
- 먼저 상단 전역 오류 banner부터 적용한다:
  - `App.tsx`의 save/navigation error
  - `Sidebar.tsx`의 build tree mutation error
- view action error(`pob-items-action-error`, `pob-skills-action-error`, `pob-config-action-error`, `pob-calcs-action-error`, `pob-party-action-error`)는 dismissible copyable banner로 통합할 후보로 둔다.
- load-blocking state error는 닫기 정책을 별도로 정한다:
  - content를 대체하는 오류 화면은 `copyable`은 제공하되 `dismissible`은 꺼두거나, 닫아도 빈 상태 설명이 남게 한다.
  - 상단 transient/action error는 `dismissible`을 켠다.
- 복사 report format은 과하지 않게 시작한다:
  - 제목: `PoB Wrapper Error Report`
  - 발생 시간
  - source/view/action label
  - 현재 build path/name이 있으면 포함
  - visible error message
  - optional details/stack이 있는 경우만 포함
- 사용자 경로가 포함될 수 있으므로 자동으로 로그 전체를 붙이지 않는다. 현재 표시된 오류와 최소 컨텍스트만 복사하고, 나중에 agent/debug log export는 별도 기능으로 둔다.
- icon은 기존 PoB UI가 쓰는 `material-symbols-outlined`의 `content_copy`, `close`를 사용한다.
- clipboard API가 없거나 실패하면 banner 내부 짧은 status 또는 기존 action notice로 실패를 표시한다.

#### 테스트 방향

- `PobErrorBanner` component test:
  - message 렌더링
  - 복사 버튼 클릭 시 `navigator.clipboard.writeText` 호출
  - 닫기 버튼 클릭 시 `onDismiss` 호출
  - `dismissible=false`면 close button 미표시
  - `copyable=false`면 copy button 미표시

  - error state가 있으면 copy/close icon이 표시된다.
  - close 후 banner가 사라지고 다음 error state update에서 다시 표시된다.
- CSS test/screenshot:
  - 긴 `EEXIST: file already exists...` 메시지에서 action buttons가 오른쪽에 유지되고 텍스트가 겹치지 않는다.
  - mobile/narrow width에서 buttons가 줄어들지 않고 message가 wrap된다.

### PR-21.10 Passive point budget summary header parity

#### 관찰

- 원본 PoB 상단 toolbar는 `Manual`, `Level`, `Class`, `Ascendancy` 컨트롤 왼쪽에 포인트 budget summary를 먼저 표시한다.
- 제보 캡처 기준 표시 순서는 `102 / 123`, weapon set 1 `0 / 24`, weapon set 2 `0 / 24`, ascendancy `2 / 8`이다.
- 첫 bucket은 일반 passive tree 포인트 사용량/최대치이며, weapon set allocation으로 양쪽에 중복 투자된 노드는 원본 계산식에서 중복 차감된다.
- 두 번째/세 번째 bucket은 각각 무기 세트 1/2에 투자한 passive 수와 사용 가능한 weapon set passive point 수다. 원본은 색상으로 bucket을 구분한다.
- 네 번째 `2 / 8`은 액트 보상 포인트가 아니라 ascendancy point 사용량/최대치다. 액트/퀘스트 보상은 별도 표시 bucket이 아니라 일반/무기세트 최대치 계산과 progress tooltip에 사용된다.
- 현재 wrapper의 `pob-build-metadata-controls`는 레벨 스케일링, 레벨, 클래스, 전직만 표시하고 point budget summary가 없다.

#### 재현 조건

- Imported Build2처럼 passive/ascendancy node가 할당된 build를 연다.
- 원본 PoB와 wrapper의 build 상단 metadata 영역을 비교한다.
- wrapper에서는 `pob-build-metadata-controls` 왼쪽에 원본 PoB의 `pointDisplay`에 해당하는 카운터가 표시되지 않는다.

#### 기대 동작

- wrapper build metadata 영역에서도 원본 PoB와 같은 bucket을 같은 의미로 표시한다.
- 표시 순서는 일반 passive, weapon set 1, weapon set 2, ascendancy 순서로 둔다.
- 최대치와 사용량은 원본 PoB `Build.lua:EstimatePlayerProgress()`와 같은 계산 결과를 Lua bridge에서 받아 표시한다. renderer가 quest reward/level/weapon set 규칙을 재구현하지 않는다.
- bucket 색상은 원본 의미를 유지한다:
  - 일반 passive와 ascendancy는 초과 사용 시 negative 색상, 정상은 기본 색상
  - weapon set 1은 원본 negative/red tone
  - weapon set 2는 원본 positive/green tone
- `Required Level`, `Estimated Progress`, `Act`, `Extra Skillpoints`, level-based ascendancy hint는 hover/focus tooltip 또는 accessible title로 제공한다.
- 레벨 스케일링 변경, level edit, class/ascendancy 변경, build load, passive tree 변경 후 metadata snapshot이 다시 로드되면 point budget도 함께 갱신된다.

#### 원인 분석

- 원본 PoB `Modules/Build.lua`는 top bar right side에서 `self.controls.pointDisplay`를 만들고, `pointDisplay.width`에서 `self:EstimatePlayerProgress()`를 호출해 표시 문자열과 tooltip 문자열을 동시에 계산한다.
- `pointDisplay`는 `levelScalingButton` 왼쪽에 배치된다. 따라서 wrapper에서도 사용자가 말한 것처럼 `pob-build-metadata-controls`의 레벨 스케일링 왼쪽에 붙는 구조가 원본 순서와 맞다.
- 원본 `EstimatePlayerProgress()`는 `self.spec:CountAllocNodes()`에서 `PointsUsed`, `AscUsed`, `SecondaryAscUsed`, `weaponSet1Used`, `weaponSet2Used`를 읽는다.
- `Classes/PassiveSpec.lua:CountAllocNodes()`는 `ClassStart`, `AscendClassStart`, `isFreeAllocate` node를 제외하고 counting한다. `node.ascendancyName`은 ascendancy bucket으로 세고, 일반 node는 `used`로 세며, `node.allocMode == 1/2`를 각각 weapon set 1/2 사용량으로 별도 집계한다.
- 원본 `Build.lua` 초기화는 `Data/QuestRewards.lua`를 순회해 `quest.questPoints`를 act별 누적한다. 현재 PoE2 데이터에서 `questPoints` entry는 `+2 Weapon Set Passive Skill Points` 보상이며, `self.maxWeaponSets = self.acts[self.maxActs].questPoints`가 된다. 캡처의 `24`는 이 누적값이다.
- 원본 일반 passive 최대치는 `usedMax = 99 + maxWeaponSets + extra`다. 여기서 `99`는 level 100 기준 레벨 포인트, `maxWeaponSets`는 퀘스트 weapon set passive point 누적, `extra`는 계산 결과의 `ExtraPoints` modifier다.
- 원본 weapon set 최대치는 `maxWeaponSets + extraWeaponSets`다. `extraWeaponSets`는 `self.calcsTab.mainOutput.PassivePointsToWeaponSetPoints`에서 온다.
- 원본 일반 passive 사용량은 `normalPassives = PointsUsed - min(weaponSet1Used, weaponSet2Used)`다. weapon set allocation이 두 세트에 모두 걸린 경우 일반 사용량에서 중복 계산을 줄이기 위한 원본 규칙으로 보인다.
- 원본 ascendancy 최대치는 `ascMax = 8`이다. `SecondaryAscUsed / secondaryAscMax`도 계산하지만, 현재 top display 문자열에는 primary ascendancy `AscUsed / ascMax`만 표시한다.
- 원본 tooltip 문자열은 `Required Level: <level>`, `Estimated Progress:`, `Act: <Act>`, `Extra Skillpoints: <extra>`와 레벨 기반 `Labyrinth` hint를 포함한다. PoE2 UI에서는 용어가 어색할 수 있어도 parity 구현은 우선 원본 계산 결과를 보존해야 한다.
- 현재 wrapper bridge `packages/pob-headless-glue/resources/lua/ipc_bridge.lua:build_metadata_snapshot()`는 `level`, `levelAutoMode`, class/ascendancy id/name, classes만 반환한다. point budget field가 없어서 renderer가 표시할 수 없다.
- shared contract `packages/shared/src/types.ts`의 `PobBuildMetadataSnapshot`과 `packages/shared/src/pobOriginalContract.ts` validator도 같은 필드만 허용한다.
- renderer `packages/pob-ui/src/views/BuildEditView.tsx`는 `pob-build-metadata-controls` 안에서 레벨 스케일링부터 렌더링하고, CSS `packages/pob-ui/src/styles.css`도 4개 column만 정의한다.

#### 수정 방향

- Lua bridge에 원본 `EstimatePlayerProgress()`를 재사용하는 projection을 추가한다. 후보 contract:
  - `passivePointBudget.normal: { used, max, exceeded }`
  - `passivePointBudget.weaponSet1: { used, max, exceeded }`
  - `passivePointBudget.weaponSet2: { used, max, exceeded }`
  - `passivePointBudget.ascendancy: { used, max, exceeded }`
  - `passivePointBudget.requiredLevel`, `act`, `extraSkillPoints`, `tooltip`
- renderer에서 원본 formatted string을 parsing하지 않고 numeric fields를 표시한다. 색상과 layout은 numeric field와 exceeded flag로 결정한다.
- bridge는 `EstimatePlayerProgress()`를 호출해 character auto-level side effect가 원본과 일치하게 유지되도록 하되, 가능하면 point budget table도 같은 local 계산식으로 함께 반환한다. 구현 시 `EstimatePlayerProgress()`의 side effect(`characterLevelAutoMode`일 때 level sync)를 의도적으로 보존할지 테스트로 고정한다.

- CSS는 metadata 전체 row를 `point budget + controls + summary` 구조로 확장한다. 좁은 폭에서는 point budget이 controls 위나 첫 row로 wrap되되, 각 숫자가 찌그러지지 않게 최소 너비를 둔다.

- 즉 PR-20은 "잠긴 mode가 있을 때 공통 marker/toast 경로를 쓰는 구조"까지만 구현했고, 사용자가 의도한 "아직 비구현인 UI version 선택을 비공식으로 고정하고 클릭 시 구현 예정 toast만 표시"는 완료되지 않았다.
- `LegacyModeView`는 실제 PoB UI parity 구현이 아니라 mode별 snapshot summary와 후속 작업 목록을 보여주는 placeholder 성격이다. 레거시 mode를 사용자가 활성 기능처럼 전환할 수 있으면 현재 완성도와 다르게 인지될 수 있다.
- PR-22 문서는 Passive Tree resource/cache/render optimization 범위만 담고 있어 UI mode lock 또는 미구현 컨트롤 inventory audit은 이관되어 있지 않다.

#### 재현 조건

- wrapper titlebar의 `UI 버전 : 레거시 [switch] 비공식` switch를 클릭한다.
- 현재 구현에서는 `LOCKED_POB_UI_MODES = []`라서 `getNextPobUiMode("renewed") === "legacy"`가 그대로 적용되고, `LegacyModeView`가 렌더링된다.
- 기대했던 공통 구현 예정 toast/status 안내와 전환 차단은 발생하지 않는다.

#### 기대 동작

- PR-21 구현 전까지 UI 기본값은 `DEFAULT_POB_UI_MODE = "renewed"` / 표시명 `비공식`을 유지한다.
- `legacy` UI가 PoB 원본 parity 수준으로 구현되기 전에는 전환이 실제로 일어나면 안 된다.
- 레거시로 전환하려는 click/keyboard activation은 `ui-mode.switch`의 공통 marker와 reason을 갖고, `buildEdit.unimplemented.notice` + `uiMode.disabled` 메시지를 표시한다.
- switch UI는 사용자가 현재 비공식 mode가 선택되어 있고 레거시가 잠겨 있음을 이해할 수 있어야 한다.
- 미구현 marker는 구현 누락 추적용이므로 busy/loading, 선택값 없음, source-disabled 같은 일시적 disabled 상태와 섞지 않는다.
- PR-20.8 inventory에 없는 미구현 컨트롤이 남아 있으면 PR-21 구현 범위에서 inventory에 추가하거나, 실제로 구현된 기능의 상태 disabled라면 marker 대상에서 제외한다.

#### 원인 분석

- `packages/pob-ui/src/views/uiMode.ts`는 `POB_UI_MODES = ["renewed", "legacy"]`, `DEFAULT_POB_UI_MODE = "renewed"`, `getNextPobUiMode()`를 제공한다.
- `packages/pob-ui/src/App.tsx`는 `useState(DEFAULT_POB_UI_MODE)`로 기본값을 비공식/renewed로 잡는다.
- 같은 파일의 `LOCKED_POB_UI_MODES: readonly PobUiMode[] = []` 때문에 `nextUiModeLocked`는 항상 false다.
- `nextUiModeLocked`가 true일 때만 `buildPobUnimplementedClassName(...)`과 `getPobUnimplementedControlAttributes("ui-mode.switch")`가 적용되고, click handler도 toast/status만 띄운 뒤 return한다.
- 따라서 공통 미구현 경로는 만들어졌지만, 실제로 잠긴 mode가 없어서 사용자 요청의 핵심 동작은 꺼져 있다.
- `PobUnimplementedButton`은 native `disabled`를 쓰지 않고 `aria-disabled`, `data-pob-unimplemented`, guarded `onClick`을 적용한다. 하지만 UI mode switch는 별도 button 구현이므로 `LOCKED_POB_UI_MODES` 정책이 실제 잠금을 결정한다.
- PR-21 구현 후 follow-up 확인에서 UI mode switch의 안내가 window-level toast가 아니라 `pob-ui-mode-notice` inline status로 titlebar 오른쪽에 렌더링되는 문제가 확인됐다. 짧은 top bar 안에서 긴 `구현 예정: ...` 문구가 언어 선택/창 버튼 영역을 밀어내므로, 미구현 안내는 각 화면 inline notice가 아니라 창 하단 공통 toast로 통일해야 한다.
- `unimplementedControls.test.ts`는 inventory id 목록과 marker attribute shape만 검증한다. `App.tsx`에서 `legacy`가 잠겨 있는지, 클릭해도 `setUiMode("legacy")`가 호출되지 않는지는 테스트하지 않는다.
- 코드 검색상 PR-20.8에서 marker가 적용된 주요 대상은 Import/Export share/character import, Tree Timeless Jewel, Items set manage/price/craft, Calcs Spectre/Beast Library다. Items DB filters처럼 단순 native disabled로 남은 요소는 실제 미구현인지 source parity placeholder인지 추가 audit이 필요하다.

#### 수정 방향

- 레거시 mode가 아직 비구현/placeholder라면 `LOCKED_POB_UI_MODES`를 `["legacy"]`로 바꾸거나, `uiMode.ts`에 mode lock policy를 두고 App에서 참조한다.
- `ui-mode.switch`는 next mode가 locked일 때 현재처럼 native `disabled`를 쓰지 않고 `aria-disabled` + guarded click/keyboard path를 유지한다. 그래야 toast/status 안내가 동작한다.
- `aria-checked`는 현재 `renewed` 선택 상태를 계속 나타내고, title/aria-label은 "레거시 UI는 아직 구현 예정"이라는 의미가 전달되게 조정한다.
- App-level `PobToast`를 두고 titlebar UI mode, Import/Export 외부 서비스 버튼, Tree/Items/Calcs의 `PobUnimplementedButton` 안내를 모두 같은 window-bottom toast로 전달한다. 각 view의 inline notice는 standalone 렌더 fallback으로만 남긴다.
- `uiMode.test.ts` 또는 App component test에 다음을 추가한다:
  - default mode가 `renewed`
  - legacy가 locked이면 switch click 후 mode가 바뀌지 않음
  - `pob-control-unimplemented`와 `data-pob-unimplemented="ui-mode.switch"`가 DOM에 있음
  - notice/status에 `uiMode.disabled` 메시지가 표시됨
- 미구현 컨트롤 inventory audit helper를 보강한다. `POB_UNIMPLEMENTED_CONTROLS`에 있는 id는 테스트에서 최소 하나 이상의 DOM marker 또는 명시적 deferred test fixture로 추적한다.
- native disabled로 남은 placeholder controls는 implementation reason을 분류한다:
  - 실제 PoB source 상태상 disabled: marker 대상 아님
  - busy/loading/invalid/empty-selection: marker 대상 아님
  - wrapper 미구현/외부 서비스/PoB parity deferred: `pob-control-unimplemented` 또는 클릭 가능한 안내 affordance 대상
- PR-20 문서에는 "현재 잠긴 mode는 없음"이라고 남아 있으므로, PR-21에서는 이 항목을 PR-20.8 follow-up으로 처리한다.
